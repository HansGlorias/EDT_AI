# Сводка ручных результатов

Это сокращённый формат итогов ручной практики по
[методике](../DEVELOPER_SCENARIOS.md), версия 1. Oracle и все 15 задач
остаются в исходном наборе. Генератор только читает два локальных файла:
он не запускает агента, модель или сетевые запросы и не собирает телеметрию.
Python 3.10+ выбран потому, что уже используется в `developer_scenarios.py`;
для JSON, проверок и Markdown достаточно стандартной библиотеки.

## Запуск

Из корня репозитория на Windows или Astra с Python 3.10+:

```text
python tools/scenario_results.py docs/scenarios/results-synthetic-baseline.json docs/scenarios/results-synthetic-candidate.json --output summary.md
python -m unittest discover -s tests/tools -v
```

На Astra команда может называться `python3`. Без `--output` отчёт идёт
в stdout (UTF-8); существующий выходной файл не перезаписывается.
Ошибка данных даёт exit code 2, отчёт не создаётся.
Оба примера **полностью синтетические**, это не результаты Qwen и не
доказательство улучшения. В них два заполненных повтора S05 из пяти.

## Файл UTF-8 JSON

Один файл — одна конфигурация и одна фиксированная группа условий
(например, одна модель с одним окном на одной машине). Для других окон
или моделей создать отдельную пару файлов. Ключи верхнего уровня обязательны:

| Поле | Значение |
|---|---|
| `schema_version` | Целое `1` |
| `synthetic` | `false` для настоящей ручной практики; `true` только для примера |
| `configuration_id` | Уникальный ID baseline или candidate, повторяется в каждой строке |
| `conditions_id` | Общий ID неизменяемых условий сравнения |
| `task_ids` | Непустой план: ID из существующего `scenarios.json`, например `["S05"]` |
| `planned_repetitions` | Число повторов на задачу; по методике `5` |
| `runs` | Массив результатов; допустим пустой массив |

ID состоят из 1–100 латинских букв, цифр, `_`, `-`, `.`. Свободных текстовых
полей нет, неизвестные поля и повторные JSON-ключи отклоняются. В файл
не помещать код, промпты, URL, токены доступа, сырые журналы или сведения
закрытого контура. Это проверка формы, не автоматическое удаление секретов.

`conditions_id` — заявление оценщика, а не вычисленный отпечаток.
До сравнения вручную сверить закреплённые конфигурации из
`configuration-template.json`: исходный архив/версию фикстур, модель,
окно клиента и сервера, генерацию/seeds, ОС/EDT/платформу/MCP, оборудование,
нагрузку, кэш/прогрев, навыки и инструменты. Разница должна быть только
в исследуемом изменении плагина. Для проверки нового профиля инструментов
отдельно закрепить именно эту единственную разницу. Полные конфигурации
и артефакты остаются локально. Генератор проверяет равенство `conditions_id`,
наборов `task_ids`, плана повторов и признака synthetic, а также разные
`configuration_id`. Содержательную идентичность условий он не доказывает.

## Одна строка runs

Обязательны `task_id`, `run_id`, `configuration_id`, `repetition`, `status`,
`success`, `measurement_complete`. Остальные поля можно опустить или
записать `null`: это **unknown**, а не ноль. Все числовые метрики — целые
неотрицательные числа (boolean и дроби отклоняются).

| Поле | Смысл |
|---|---|
| `run_id` | Уникальный ID во всей паре файлов |
| `task_id`, `repetition` | Задача из плана, повтор от 1 до `planned_repetitions`; слот уникален |
| `status` | `pass`, `partial`, `fail`, `timeout`, `blocked_environment`, `not_run` по методике |
| `success` | Boolean, `true` только для `pass` после всех проверок oracle |
| `edits_correct` | `true`/`false` по проверке diff/буфера; `null` если неприменимо или не проверено |
| `measurement_complete` | Boolean: подтверждён полный захват задачи, включая сжатие, название, ошибки и скрытые попытки |
| `server_input_tokens`, `server_output_tokens` | Независимые известные суммы серверного usage по физическим запросам |
| `server_input_requests`, `server_output_requests` | Число физических запросов, для которых известна соответствующая серверная сумма |
| `estimated_input_tokens`, `estimated_output_tokens` | Независимые суммы оценок, никогда не прибавляются к server |
| `estimated_input_requests`, `estimated_output_requests` | Покрытие соответствующей оценки физическими запросами |
| `estimate_method` | ID метода **с версией**, например `chars-div3-v1`; обязателен при оценках |
| `model_requests` | Все известные физические запросы: ответ, сжатие, название, неудачные попытки |
| `tool_calls` | Число решений модели вызвать инструмент (logical calls), включая отказанные/заблокированные |
| `tool_executions` | Фактические исполнения; отказ/заблокированный дубль исполнением не является |
| `mcp_transport_attempts` | Все попытки MCP; initialize, tools/list и tools/call, в том числе переподключение |
| `repeats` | Повторные решения модели вызвать тот же инструмент с теми же аргументами после первого; включает разрешённое перечитывание и заблокированные дубли, без внутренних transport retries |
| `duration_ms` | elapsed от первого промпта до конца прогона/проверки oracle; включает ожидание человека |
| `first_visible_ms` | От первого промпта до первого видимого текста ответа; без индикаторов и скрытого reasoning |

Записывать `measurement_complete=false`, если доступна только лента EDT
или часть журналов. `model_requests` тогда известный подытог; неизвестные
скрытые попытки не восстанавливаются из ленты. Покрытие запросов не больше
`model_requests`; токены и соответствующее покрытие заполняются вместе.
При положительном числе запросов покрытие 0 записывается как `null/null`,
поскольку известного usage нет. Измеренный ноль допустим: например,
нулевой output при положительном покрытии. Ноль запросов с нулём токенов
и покрытием 0 допустим только как фактически измеренное значение.

Считать серверную величину один раз на запрос, сохраняя исходный usage
локально. Не прибавлять cache/reasoning второй раз, если они уже включены
сервером. Если нет уверенности в полном output с reasoning — это
неполное измерение. Оценка видимого текста reasoning не восстанавливает.
Оценки могут диагностически покрывать и запросы с usage, но в отчёте
остаются отдельными. Разные методы оценки видны в таблице; для сравнения
их следует держать одинаковыми. Полноценный аудит покрытия/дедупликации
запросов остаётся в подробных `requests.csv` и `tools.csv`.

Для `not_run` и `blocked_environment` — `success=false`,
`measurement_complete=false`, все метрики и `edits_correct` — null.
Если сбой случился после начала подготовленного прогона, это fail/timeout,
его затраты сохраняются. `pass` несовместим с `edits_correct=false`.
`first_visible_ms` не может превышать `duration_ms`.

## Как читать отчёт

Строки сгруппированы по задаче, без смешения задач настоящего EDT-MCP
с тестовым MCP. Успех делится на **весь план**, не только на начатые
прогоны. Пропущенные слоты считаются `not_run`; явные blocked/not_run
сохраняются. Рядом показаны начатые/план и каждый прочий статус.
Корректность правок — правильные/оценённые с покрытием относительно плана;
null не засчитывается как правильная правка.

Полная сумма server input+output берётся только по **одинаковым повторам**,
полностью измеренным в обеих конфигурациях с usage каждого запроса.
Их номера и размер выборки перечислены. Неполные прогоны туда не входят.
В остальных столбцах — известные подытоги каждой стороны и покрытие
запросов/прогонов. `>=` у знаменателя означает, что часть запросов могла
остаться невидимой. Суммы server и estimate никогда не объединяются.
Счётчики также показывают покрытие; строка неполного измерения не становится
полной стоимостью из-за наличия чисел.

Время успехов и неудач показано отдельно: медиана, min/max, покрытие;
дополнительно сохраняется сумма времени неудач. `duration_ms` не является
active_ms или оценкой скорости генерации. Полные интервалы человеческих
ожиданий остаются в `human-waits.csv`. При разном покрытии нельзя выдавать
изменение подытога за экономию. Пять повторов не доказывают статистическую
значимость; результаты нужны для практики и воспроизводимого фидбека.
