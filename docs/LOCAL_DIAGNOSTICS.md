# Фундамент локальной диагностики

Инфраструктура `core.diagnostics.DiagnosticEvent`/`DiagnosticLog` подключена
к физическим запросам ModelClient через opt-in sink и ограниченный
асинхронный контроллер UI. По умолчанию запись выключена. Жизненный цикл
событий, run ID, источники usage и границы учёта — в
[DIAGNOSTICS.md](DIAGNOSTICS.md).

## Маленький API

- `new DiagnosticLog()` — выключен, файловую систему не трогает.
- `DiagnosticLog.open(Path)` — явное включение; путь выбирает вызывающий код.
  Создаёт родительский каталог и активный файл. Проверяется через `state()`.
- `write(DiagnosticEvent)` возвращает состояние после синхронной записи.
- `state()` — `DISABLED`, `AVAILABLE`, `UNAVAILABLE`, `CLOSED`.
- `close()` — идемпотентный, освобождает дескриптор; поддержан try-with-resources.

Событие описывает **один завершённый запрос**, а не весь ответ агента.
Один ответ с инструментами может потребовать нескольких запросов.
`Id.random()` создаёт непрозрачный UUID v4: один для запуска ответа (`runId`),
отдельный для каждой попытки запроса (`requestId`). Фабрики из строки нет.
Нельзя подставлять ID сервера, сохранённого чата или проекта. Writer не
создаёт связи с ними и не проверяет жизненный цикл ID; вызывающий
код отвечает за повторное использование run ID и уникальность request ID.

## Схема JSONL, версия 1

Одна строка — один компактный JSON-объект, UTF-8 без BOM, завершается LF
на обеих ОС. Кодирование — существующим `core.json.Json`.
Все поля обязательны, дополнительных полей и вложенного payload нет.

| Поле | Значение |
|---|---|
| `version` | целое `1` |
| `run_id`, `request_id` | случайные UUID v4, созданные `Id.random()` |
| `request_type` | `answer`, `title`, `summary`, `retry`, `check` |
| `status` | `success`, `cancelled`, `failed`, `timeout`, `rejected` |
| `duration_ms` | длительность запроса в миллисекундах |
| `request_bytes`, `response_bytes` | прочитанные/подготовленные размеры тела в байтах без заголовков; null если неизвестны |
| `tool_calls` | число предложенных calls полного reply, не выполненных инструментов |
| `retries` | ordinal внутри логического шага: `0` исходная, `1` первый повтор; не суммировать |
| `input_tokens`, `output_tokens` | объект `{"value":…, "provenance":…}` |

Длительности и количества — Java long от0 до Long.MAX_VALUE. Размеры —
nullable Long того же диапазона; неизвестное значение строго null, не0.
Версия1 расширена этим допустимым значением без добавления JSON-ключей.
Writer не вычисляет суммы или размеры. JSON long при чтении JavaScript может
требовать парсера без потери точности.

Для каждого счётчика токенов источник задан отдельно:

- `server` — `value` от 0 до `Long.MAX_VALUE`, данные usage сервера;
- `estimate` — такой же диапазон, оценка вызывающего кода;
- `unknown` — строго `value: null`, достоверного числа нет.

Известный ноль не является отсутствием usage. Серверный вход и оценённый
выход могут присутствовать в одном событии. Writer не преобразует
`TokenUsage`, не складывает источники и не определяет семантику кэша сервера.
Отдельных полей кэша и reasoning в этой версии нет.

Контракт Java принимает только непрозрачные ID, enum, числа и записи
`Tokens`. Нет свободных строк, произвольных Map, расширяемых полей,
payload/error или Throwable. Тексты промптов, модели и ошибок, аргументы
и результаты инструментов, endpoint, заголовки, пути проекта, имя модели
и секреты передать через публичный контракт события нельзя. Путь журнала
не сериализуется, исключения записи нигде не логируются.

## Хранение и отказ

Верхние границы фиксированы публичными константами, не настройками:
**1 048 576 байт на файл, 3 файла вместе с активным, всего до 3 МиБ**.
Для пути `metrics.jsonl` принадлежат журналу только `metrics.jsonl`,
`metrics.jsonl.1`, `metrics.jsonl.2`. Вызывающий код должен выделить
собственный путь и единственного владельца; несколько экземпляров или
процессов на одном пути и внешние изменения файлов не поддерживаются.
Глобального singleton, фонового потока, очереди, таймера и сети нет.

Перед записью целой строки проверяется размер в UTF-8. Если она не
помещается, активный файл закрывается, `.2` удаляется, `.1` переходит в
`.2`, активный — в `.1`, создаётся новый активный. Старейшее удаляется
перед перемещениями, поэтому временного четвёртого файла нет. Запись,
ротация, state и close синхронизированы на экземпляре: параллельные
вызовы не перемешивают строки. После каждой строки вызывается flush;
fsync и гарантия сохранности при отключении питания не предоставляются.

При открытии проверяются все три занятых имени: только обычные файлы
без symlink, каждый не больше лимита. Нарушение даёт `UNAVAILABLE` без
удаления этих файлов. Корректный активный журнал ротируется при открытии,
новая сессия начинает новый файл. Поэтому данные прошлого запуска
остаются ограничены теми же тремя файлами. Чужие имена не сканируются
и не удаляются; уже существующие посторонние/слишком большие файлы не
входят в гарантию размера созданного writer хранилища.

IOException или SecurityException при открытии, записи, flush, ротации
или close не выходят к вызывающему коду. Состояние становится
`UNAVAILABLE`, дескриптор закрывается по возможности; последующие write
и close не пытаются открыть или записать файл заново. Нет сообщения
исключения, пути или стека в API статуса. Некорректные аргументы API
(например, отрицательные числа или null обязательного поля) — ошибки
программирования и отклоняются при создании события.

После частичной записи при I/O-сбое или аварийном завершении последняя
строка может быть неполной; читатель должен уметь пропустить её.
Атомарность нескольких перемещений при аварии не гарантируется, возможна
потеря последних событий. Это вспомогательная диагностика, не журнал
подтверждённого выполнения операций. Синхронная файловая запись может
задержать поток; интеграция передаёт её отдельному I/O worker, не SWT UI thread.

## Проверки и следующий этап

`DiagnosticLogTest`: выключение без файлов, точная схема и отсутствие
свободных полей, UUID, null/отрицательные значения, все enum и provenance,
границы при ротации и повторном открытии, реальные публичные лимиты,
800 конкурентных записей без потерь, ошибки open/write/flush/close/
rotation, отсутствие повторных попыток, идемпотентное закрытие и
освобождение файла на Windows. Тесты ядра, без SWT и сервера модели.

Opt-in настройка, владение writer и точки запросов ответа, названия,
сжатия и повтора подключены и проверяются фейковым сервером.
Следующий этап — корреляция полных пользовательских задач.
