# Демо EDT AI на рабочем проекте

Показ на настоящем проекте в своём dev-окружении: рабочая конфигурация
в EDT и её git-репозиторий. Модель — недорогая китайская через
OpenAI-совместимый шлюз. Цель — показать работу с живым кодом 1С:
разобраться, найти, проверить, поправить и закоммитить.

Измерения качества и токенов на фиксированных задачах — отдельно,
в [DEVELOPER_SCENARIOS.md](DEVELOPER_SCENARIOS.md). Здесь не замер, а показ.

## Накануне: 30–40 минут

### Сборка и модель

- EDT AI из `main` не старше #81: в нём рассуждение модели возвращается
  в цикл инструментов. Без этого DeepSeek и Kimi падают с 400 после
  первого вызова инструмента. Zip — артефакт `edtai-update-site` из CI
  нужного SHA, установка — [install-pr-build.md](install-pr-build.md).
- Протокол OpenAI-совместимый. Основная модель — **Qwen3.8 Flash**,
  запасная — **DeepSeek V4 Flash**; если обе не вызывают инструменты —
  MiniMax M3 или GLM 5.3 Flash. Обе выбранные модели один раз выбрать в
  `/model`, чтобы они были в недавних и переключались за секунду.
- **Макс. токенов ответа — 8192.** Рассуждение тратит тот же лимит,
  с 2048 модель часто не доходит до ответа («Ответ оборван»).
- «Проверить подключение» в настройках → ответ за разумное время.
- Режим **Агент**, авторежим MCP **выключен** (каждый вызов MCP и каждая
  запись — с подтверждением).
- **EDT-MCP — только нужные инструменты**, см. раздел ниже. Остальные
  серверы MCP отключить: индикатор должен быть зелёным, не «1/2».

### EDT-MCP: что оставить

У [EDT-MCP](https://github.com/DitriXNew/EDT-MCP) около 100 инструментов.
Описание каждого уходит в каждый запрос, а часть дублирует встроенные:
небольшая модель путается, чем читать и искать, и угадывает аргументы.
В настройках EDT AI → MCP → сервер EDT-MCP → поле **«Инструменты»**
вставить строку целиком (разделитель — `;`, запятая или пробел):

```text
get_method_call_hierarchy; find_references; go_to_definition; get_symbol_info; get_module_structure; read_method_source; get_metadata_details; get_project_errors; validate_query; get_platform_documentation; get_tool_guide
```

| Инструмент | Зачем, чего нет во встроенных |
|---|---|
| `get_method_call_hierarchy` | Кто вызывает метод и что вызывает он — по модели EDT, без комментариев и одноимённых методов (кейсы 1, 2) |
| `find_references` | Где используется объект метаданных: код, формы, роли, подписки |
| `go_to_definition` | Где определён символ или объект |
| `get_symbol_info` | Тип и документация символа в точке кода |
| `get_module_structure` | Области, методы, экспорт, контексты модуля — без чтения всего текста |
| `read_method_source` | Один метод по имени: модуль формы на 400 КБ не тянуть целиком |
| `get_metadata_details` | Реквизиты, табличные части, типы, свойства форм |
| `get_project_errors` | Ошибки и предупреждения проверки EDT, в том числе после правки (кейсы 5, 7) |
| `validate_query` | Синтаксис запроса и ссылки на метаданные (кейс 6) |
| `get_platform_documentation` | Справка по типам и функциям платформы — против выдуманных методов |
| `get_tool_guide` | Параметры и примеры инструментов EDT-MCP: их описания короткие и отсылают сюда |

Не давать модели:

- **дубли встроенных**: `read_module_source` (= `read_module`),
  `search_in_code` (= `search_code`), `list_modules` и
  `get_metadata_objects` (= `list_objects`), `list_projects`
  (= `project_info`), `write_module_source` (= `edit_module`), `git`,
  `list_git_branches` (= `git_*`);
- **меняющие проект и базу**: создание, изменение, переименование и
  удаление метаданных и проектов, `update_database`, импорт и экспорт,
  перевод, `clean_project`, `resync_to_disk`, `apply_quick_fix`;
- **отладку, запуск и базы**: `launch`, `debug_*`, `step`, точки
  останова, профилирование, тесты, информационные базы, сеансы, журнал
  регистрации — для показа не нужны;
- **остальное** (теги, картинки, СКД, скриншоты форм, служебное) —
  включать под конкретную задачу, не по умолчанию.

На репетиции проверить, что в `/mcp` у EDT-MCP видны 11 инструментов
и что первый вызов любого из них проходит.

### Рабочая копия

```bash
git status --short
```

Пусто — иначе закоммитить или убрать в stash свою работу. Затем ветка
только для показа:

```bash
git switch -c demo/edt-ai
```

После показа — вернуться и удалить её (`git switch -` и
`git branch -D demo/edt-ai`). Remote не трогаем, push не делаем.

### Экран

- Настройки EDT AI на проекторе **не открывать**: там адрес шлюза.
  Подключение проверить заранее.
- Старые чаты закрыть или свернуть панель чатов; каждый кейс — `/new`.
- Шрифт редактора и ленты — крупнее обычного.

### Выбрать объекты под кейсы

Самое важное в подготовке. Кейсы ниже работают на любом проекте, но
заранее нужно выбрать конкретные места и **один раз прогнать каждый
кейс**. На показ взять то, что сработало. Таблицу заполнить у себя,
не в репозитории.

| Кейс | Что выбрать | Критерий | Выбрано |
|---|---|---|---|
| 1 | Модуль «страшилка» и метод в нём | 100–300 строк метода, вызывает 2–5 своих функций из других модулей | |
| 2 | Экспортная функция | 3–15 вызовов по проекту; не общая процедура БСП с сотнями вызовов | |
| 3 | Модуль с историей | 5+ коммитов разных авторов, последний — понятный по смыслу | |
| 4 | Место для «закладки» | Метод, где ошибку видно без контекста (см. ниже) | |
| 5 | Место для правки | Функция без проверки параметра или с повторяющимся куском | |
| 6 | Запрос | Запрос в цикле или запрос с лишними соединениями | |

## Кейсы

Формулировки — пример; подставить свои имена. Время — с ответом модели.

### 1. Разобраться в чужом коде — 2–3 мин

Открыть модуль, выделить метод целиком → ПКМ → **EDT AI → Объяснить**
(или `/explain` в поле ввода).

Уточнение, если нужно глубже:

> Что этот метод делает по шагам и какие функции других модулей вызывает? Для каждой — одной строкой, что она возвращает.

**Что видно:** модель сама читает вызываемые функции (`read_module`
в ленте), ссылки «Модуль:строка» кликабельны и открывают редактор.
**Подвох:** если метод маленький и всё очевидно — эффекта нет. Нужен
метод, в котором зрители сами не сразу разберутся.

### 2. Что сломается, если поменять — 2–3 мин

> Где вызывается ОбщийМодуль.<Модуль>.<Функция>? Если добавить ей обязательный параметр, какие места придётся поменять? Список с модулем и строкой, код не меняй.

**Что видно:** `search_code`, затем чтение мест вызова, список с
ссылками. Перейти по паре ссылок. **Подвох:** функция с сотнями вызовов
даст «показаны первые N» — выбрать узкую.

### 3. История из репозитория — 2 мин

> Кто и когда последним менял <Модуль>? Что именно изменил последний коммит и зачем, судя по коду?

**Что видно:** `git_log` по модулю, `git_diff` по коммиту, пересказ
смысла правки. Хорошо заходит: «новый человек в команде спрашивает,
почему здесь так».

### 4. Ревью с маркерами — 3 мин

Накануне в ветке `demo/edt-ai` внести в выбранный метод одну
правдоподобную ошибку и **не коммитить** её. Варианты:

- `>` вместо `>=` в проверке остатка или суммы;
- запрос внутри цикла `Для Каждого`;
- `Попытка … Исключение КонецПопытки` без записи в журнал;
- серверный вызов в обработчике формы на каждое изменение поля.

На показе: `/review` — ревью незакоммиченного. Без закладки можно
выделить код и ПКМ → **EDT AI → Ревью**, но тогда результат заранее
не известен.

**Что видно:** модель смотрит `git_diff`, читает окружение, карточка
ревью в ленте и **маркеры в редакторе** на строках; щелчок по маркеру
в «Проблемах» открывает строку. Закладку видно в diff — честно сказать,
что её внесли заранее. Найденное сверх неё — бонус.

### 5. Правка, diff и коммит — 3–4 мин

> В <Модуль>.<Функция> добавь проверку: если <Параметр> не заполнен — ВызватьИсключение с понятным текстом. Больше ничего не меняй. Прочитай результат после правки.

Подтвердить запись в панели подтверждения. Затем:

1. «Изменения» в заголовке ответа — окно сравнения до/после.
2. `/commit` — сообщение коммита по незакоммиченному (или кнопка
   «Написать сообщение коммита» на панели Git Staging).
3. Откат: «Откатить» в заголовке ответа (или `git restore` / EGit).

**Что видно:** запись только после подтверждения, точечный diff,
готовое сообщение коммита. **Подвох:** если модель переписала лишнее —
не скрывать: показать diff, откатить, это тоже честная демонстрация
контроля.

### 6. Запрос — 2 мин, по желанию

Выделить запрос в редакторе → ПКМ → **EDT AI → Спросить о выделенном**:

> Почему этот запрос может быть медленным? Предложи исправленный текст запроса, в модуль не записывай.

Работает навык `query-optimize` / `query-style` (если навыки включены).

### 7. EDT-MCP — 2 мин, только если проверен накануне

После кейса 5, до отката:

> Проверь проект на ошибки после этой правки.

Подтвердить вызов MCP (`get_project_errors`). Если EDT-MCP не отвечает накануне — кейс не
показывать, индикатор MCP не обещает, что операция пройдёт.

## План показа

**15 минут:** вступление 1 → кейс 1 (3) → кейс 2 (3) → кейс 4 (3) →
кейс 5 (4) → итог 1.

**10 минут:** кейсы 1, 4, 5.

**20 минут:** добавить кейсы 3 и 6 (или 7), между 2 и 4.

Порядок важен: сначала только чтение (безопасно, разогрев), потом ревью,
в конце запись с подтверждением и откатом.

## Если что-то пошло не так

| Что | Что делать |
|---|---|
| Модель молчит дольше 1,5–2 мин | «Стоп», `/model` → запасная, `/new`, тот же вопрос |
| 400 / «сервер не принимает инструменты» | Запасная модель. Не чинить на сцене |
| «Ответ оборван» | Повторить с меньшим вопросом; лимит ответа проверить после показа |
| Модель выдумала метод или модуль | Кликнуть ссылку, показать, что его нет, и спросить «проверь чтением» — это демонстрирует, зачем инструменты |
| Правка затронула лишнее | Показать diff, «Откатить» |
| Совсем не работает | Кейсы 1–3 рассказать на открытом коде и показать ленту репетиции, назвав её записью |

## Что говорить

- **Вступление.** «Чат с моделью прямо в EDT. Модель сама читает модули,
  ищет по проекту, смотрит git, делает ревью и правит — с нашим
  подтверждением. Показываю на нашем проекте и на недорогой модели».
- **По ходу.** Показывать ленту: какие инструменты вызвала модель —
  это ответ на «а она не выдумывает?».
- **Итог.** «Сегодня на этой модели работает: объяснение, поиск влияния,
  ревью, точечная правка с diff и откатом. Чего нет: гарантий качества на
  любом коде — модель ошибается, поэтому записи только с подтверждением и
  с diff. Дальше: замеры на наших задачах, подбор модели и набора
  инструментов под небольшое окно».

Не обещать проценты экономии, «работает на любой модели» и автономную
работу без подтверждений.
