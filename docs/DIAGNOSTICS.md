# Диагностика физических запросов

ModelClient принимает необязательный `Consumer<DiagnosticEvent>`. Прежние
конструкторы сохраняются и не создают trace ID, не пересчитывают UTF-8 размер
для диагностики и не оборачивают поток счётчиком. Подключённый sink получает
события синхронно на worker, на caller при локальном отказе или отмене;
он обязан не блокировать. Исключения sink не меняют исход запроса.
Дополнительный overload принимает BooleanSupplier enabled: включение фиксируется
при создании run/standalone-запроса. При off не создаются IDs и счётчик;
включение посередине AgentLoop действует со следующего run, отключение UI
сразу отбрасывает callbacks. Ошибка predicate означает off.
UI передаёт события ограниченному асинхронному контроллеру, который учитывает
явное включение пользователем и не пишет журнал по умолчанию.

## Событие и область учёта

На физическую попытку запроса или локальный отказ подготовки приходится одно
terminal-событие. Success, failure и cancellation используют общее владение
завершением: событие фиксируется до завершения physical future, гонка отмены
не создаёт вторую строку. Таймер — монотонный System.nanoTime.

- `answer`: очередной модельный шаг; `retry`: повтор того же логического шага
  после серверного отказа; `title`, `summary`, `check`: служебные запросы.
- Один случайный run_id объединяет шаги и повторы одного AgentLoop. Каждый
  request_id новый. Название, сжатие и проверка подключения пока получают
  отдельные run_id; полная стоимость пользовательской задачи не вычисляется.
- `retries` — ordinal попытки внутри логического шага: 0 исходная, 1 первый
  повтор и т. д. При новом шаге снова 0. Складывать это поле как число повторов
  нельзя; фактические повторные попытки можно считать по request_type=retry.
- `tool_calls` — число предложенных моделью вызовов в полном reply. Это не
  число выполненных инструментов. При отсутствии полного reply — 0; telemetry
  исполнения инструментов в этом этапе нет.

## Размеры и токены

`request_bytes` — UTF-8 длина сохранённого PreparedRequest, не токены и не
длина UTF-16 строки. `response_bytes` — прочитанные байты тела HTTP-ответа
после удаления HTTP chunk framing, без заголовков. SSE управляющие события,
usage и JSON входят в этот размер, а не только видимый текст. При отмене это
безопасный опубликованный счётчик прочитанного на момент terminal-снимка;
не читаются mutable SSE parser или незавершённые tool builders.

На SUCCESS используются серверные поля usage с раздельным provenance. Только
отсутствующая половина дополняется явно обозначенной оценкой из того же
PreparedRequest и прежней эвристики AgentLoop. Серверный ноль сохраняется.
При FAILED/TIMEOUT/CANCELLED/REJECTED usage неизвестен; частичные данные потока
не объявляются финальным расходом. Локальный guard даёт REJECTED без HTTP.

Закрытая JSONL схема остаётся версии1 и с теми же ключами; допускается null
у request_bytes/response_bytes, если размер неизвестен (например, ошибка
сериализации до снимка). Это расширение допустимых значений v1: читатель
должен различать null и измеренный0. При локальном отказе с готовым снимком
известны request_bytes и response_bytes=0; до подготовки входной размер может
быть неизвестен. Подробности writer, ротации и ограничений —
[LOCAL_DIAGNOSTICS.md](LOCAL_DIAGNOSTICS.md).

Журнал не содержит endpoint, имени модели, ID сервера/чата/проекта, заголовков,
токенов доступа, кода, промптов, ответов, reasoning, аргументов/результатов
инструментов и текстов ошибок. First byte, операции инструментов, связь
служебных run с ответом и полные task totals остаются отдельной работой.
