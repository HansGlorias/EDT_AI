# EDT AI: следующий архитектурный этап

Актуальная основа: `origin/main` после PR #78 (`4b9bf41`, 02.11.2026).
Архитектурная ветка — `codex/request-budget-guard` в отдельной рабочей копии.
Смежные изменения MCP уже в main (#76).

## Завершено в #74: достоверность частичного usage
- Для input/output/context сохраняется отдельный источник: SERVER, ESTIMATE,
  UNKNOWN или MIXED (сумма серверных чисел и оценок). Неполная сумма остаётся UNKNOWN.
- Отсутствующее поле не показывается точным нулём; серверный ноль сохраняется.
  AgentLoop оценивает только отсутствующую половину, сохраняя известную.
- Расход input/output суммируется по шагам ответа; context и его источник
  относятся только к последнему физическому запросу.
- История читает прежний `estimated` и сохраняет новые источники. Повреждённые
  метрики не должны препятствовать восстановлению сообщений и результатов.
- Бюджет, название/сжатие и полная стоимость задачи остались за пределами #74.
- Локально — целевые core-тесты и проверка diff; полный verify Windows/Ubuntu
  обязателен в CI перед мержем (политика проекта после #70).

## Основа #78: снимок физического запроса
- Package-private immutable PreparedRequest хранит сериализованное финальное
  JSON-тело; ModelClient отправляет именно эту строку без пересборки.
- Размер JSON в UTF-16 символах, UTF-8 байты и оценка входных токенов — разные
  метрики. Прежняя эвристика картинок применяется только к блокам в payload.
- AgentLoop после fit и путь без инструментов используют тот же снимок для
  оценки отсутствующего usage; известные серверные значения сохраняются.
- Метаданные: число схем и фактически включённый max_tokens (для OpenAI
  default может отсутствовать). Подключение/токен не хранятся в снимке,
  toString не раскрывает тело. Входы не менять конкурентно во время prepare.
- Формулы бюджета, max_tokens, include_usage и wire-поля не меняются.
  Это основа достоверного учёта, а не полное решение отображения контекста
  или общей стоимости задачи. Диагностика к HTTP пока не подключена.

## Текущий небольшой PR: проверка бюджета до HTTP
- [Контракт и ошибки бюджета](REQUEST_BUDGET_NEXT.md): резервировать фактически
  отправленный max_tokens целиком. Anthropic default8192 сохраняется; в окне8k
  это локальная ошибка настройки. OpenAI default остаётся без wire max_tokens,
  резерв min(4096, окно/4) явно предположительный.
- Общий ModelClient guard применяется и к служебным запросам; AgentLoop
  дополнительно проверяет уменьшенный бюджет после серверного отказа.
  Минимальный запрос не помещается — ошибка до HTTP, без повторной записи
  инструментами или потери журнала/call-result пар.
- Формула бюджета больше не выделяет искусственную четверть окна поверх
  невозможного резерва. Это оценка, не гарантия серверной токенизации.
- Категории состава запроса, UI счётчик контекста, полная стоимость задачи
  и подключение диагностики остаются отдельными этапами.

## Приоритеты архитектуры
1. Достоверный учёт: разделить последний физический запрос, оценку следующего запроса и суммарную стоимость задачи. Не подменять отсутствующий usage нулём. Источник входных и выходных чисел учитывать раздельно.
2. Единый PreparedRequest: зафиксировать фактическое тело запроса, состав контекста и резерв ответа перед отправкой. Использовать его для бюджета и диагностических метрик. Символы/UTF-8 байты/токены не смешивать.
3. Общий бюджет: явная обработка непомещающегося минимального запроса; сохранение цели, ссылок и call/result пар. Устранить расхождение резерва ответа с фактически отправляемым max_tokens.
4. Steering: уточнения поступают в текущий RunControl, а не в очередь нового ответа. Сохраняются ledger и снимки. Запрос модели можно отменить и пересобрать, уже исполняемую запись нельзя считать отменённой или безопасной для повтора.
5. Rewind: отдельная ветвь диалога от выбранной точки, исходная ветвь сохранена. Никакого неявного отката файлов; код читается заново как актуальный.

## Подтверждённые проблемы счётчика
- ModelChatProvider.estimateTokens не включает инструменты, их результаты и сведения о проекте.
- ChatSession.restore сбрасывает usage, UI переходит на оценку истории.
- Подмена отсутствующей половины usage нулём в StreamState/адаптерах исправлена в #74.
- TokenUsage.context относится к последнему шагу, а не сумме расхода задачи.
- OpenAI-совместимый поток не запрашивает stream_options.include_usage. Добавление требует проверки совместимости серверов, не автоматического повтора любого 400.
Наблюдение пользователя «1k после ревью двух коммитов» пока не диагностировано по конкретной трассе.

## Контракт steering
- Различать Stop всей задачи и обновление её инструкций.
- Принимаемые сообщения упорядочены, включают контекст и вложения; новый ввод не стирает предыдущие ограничения.
- Использовать номер ревизии ввода: устаревший ответ модели не запускает инструменты после получения уточнения.
- При уточнении во время записи дождаться известного исхода; не запускать вторую запись параллельно.
- При уточнении во время разрешения отменить устаревший запрос разрешения без записи постоянного отказа пользователя.
- Для уже частично выполненного пакета сохранить call/result пары, явно пометить невыполненные операции.
- На следующей границе шага добавить уточнение и сделать новый запрос с прежним журналом операций.
- Тестировать fake server: до первого байта, в потоке текста, между tool calls, в approval, во время записи, несколько уточнений, отмена, фоновые чаты.
- Нужны отдельные замеры реальной модели: скорость реакции и сохранение новых требований.

## Диагностика
- Первым этапом локальная ограниченная трасса метаданных по явному включению пользователя.
- run_id / request_id / тип запроса (ответ, название, сжатие, повтор) / время начала и первого видимого текста / длительность / статус.
- Состав отправленного контекста по категориям в символах/байтах; schema count; страницы результатов; входной/выходной usage с происхождением каждого поля; размер окна и источник настройки.
- Инструменты: имя, длительность, статус, число физических попыток, размеры аргументов и результатов, факт усечения/дочитывания. Не сохранять аргументы и результаты.
- Не записывать токены доступа, заголовки, endpoint, пути файлов, код, промпты, ответы, reasoning или сырые ошибки по умолчанию.
- Ограничение размера/ротация, явный экспорт выбранной задачи. Полные содержательные трассы — отдельное осознанное действие, не часть первого этапа.
- Практический фидбек связывать с run_id и исходом задачи по DEVELOPER_SCENARIOS.md. Автотесты Java не заменяют проверку Qwen.
