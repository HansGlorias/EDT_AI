# Воспроизводимые задачи разработчика 1С

Версия набора: 1. Это фикстуры и методика сравнения изменений EDT AI.
Реальные результаты Qwen сюда пока не внесены. Зелёный JUnit проверяет
Java-механизмы и целостность набора, а качество модели измеряется отдельно.

## Где лежат данные

Единственный источник точных промптов, исходного состояния, разрешённых
изменений, проверяемых фактов и провалов — [scenarios.json](../tests/io.github.hansglorias.edtai.core.tests/fixtures/developer-scenarios/scenarios.json).
Исходники и эталоны находятся рядом с ним. В дальнейшем этот каталог
обозначается `F`. Строки в карточках считаются с 1, включая комментарии.

| ID | Задача | Проверка результата |
|---|---|---|
| S01 | Объяснение выделения | Фрагмент 8–10, сумма 337,5, округление |
| S02 | Поиск реализации | Функция РасчетыЗаказов, а не одноимённая демонстрационная |
| S03 | Места вызова | Два вызова; строка, комментарий и одноимённый метод исключены |
| S04 | Ошибка по стеку | Строка 19, деление на ноль, воспроизводящий вход |
| S05 | Малая правка | Только точность Окр: 2 → 0; чтение после записи |
| S06 | Неуникальный old_text | Только текст для журнала; неоднозначная замена ничего не пишет |
| S07 | Несохранённый буфер | Новая подпись, сохранены скидка 7 и билет 314; диск прежний |
| S08 | Объяснение запроса | Пакеты, ВТ, отбор; коды В, Г |
| S09 | Изменение запроса | Включительная верхняя граница; код Г |
| S10 | Метод платформы | Настоящая справка: Массив.Найти, отсутствие НайтиПервый |
| S11 | Ревью diff | Одна ошибка на строке 7; карточка и маркер; без правки |
| S12 | Диагностика EDT-MCP | Версия совпадает с независимым контрольным вызовом |
| S13 | Временный сбой | Восстановление сессии; два transport tools/call, один полезный результат |
| S14 | Длинный диалог | Сжатие сохраняет цель и выполненное; правится только оставшееся |
| S15 | Отмена и продолжение | После Стоп нет записи; продолжение читает состояние и завершает правку |

Промпт удобно вывести без ручного поиска (Python 3.10+, стандартная библиотека):

```text
python tools/developer_scenarios.py show S06
```

Все пункты `oracle.facts` обязательны для `pass`. Неверный факт или
запрещённая правка — `fail`; неполное объяснение, отсутствие подтверждённого
чтения/проверки — `partial`. Проверка текста ответа по ключевым словам
сама по себе не является oracle. Оценщик сверяет факты, ссылки и трассу,
не получает название сравниваемой версии плагина. Для спорного ответа
сохраняются решение и причина второго оценщика.

## Два независимых вида проверки

1. **Java и протоколы, без настоящей модели.**
   `DeveloperScenariosTest` загружает ровно эти исходники: реальный поиск,
   отказ неоднозначной замены, точные изменения, BOM/LF/CRLF, контракт
   несохранённого текста, настоящий git diff, загрузка длинной истории
   и порог сжатия на 8192/16384/32768. Адаптер буфера в этом тесте
   не проверяет SWT: dirty и отмена редактора остаются ручной проверкой.
   Java-фильтрация query-data.json проверяет контрольные данные,
   но не исполняет и не компилирует язык запросов 1С.
   DeveloperScenarioProtocolTest проводит S05 через настоящий цикл
   инструментов с fake model в обоих протоколах на трёх окнах и
   проверяет отдельные физические запросы ответа, сжатия и названия.
2. **Настоящая Qwen, полный путь через EDT AI.**
   Оценка смысла ответа, выбора инструментов, правок, поведения после
   сжатия и отмены. Фиксированные ответы fake model не засчитываются
   как успешные задачи модели. S13/S15 используют управляемый тестовый
   MCP, а S10/S12 — настоящий EDT-MCP и установленную платформу.
   Эти строки результатов нельзя объединять как замер реального EDT-MCP.

Существующие `ModelClientTest`/`AgentLoopTest` проверяют OpenAI-совместимый
и Anthropic-протоколы, SSE/JSON, ошибки и usage. `AgentExecutionTest`
проверяет временный сбой безопасного чтения, неопределённый исход записи,
обрезку контекста и отмену между вызовами. `McpHubTest` — JSON/SSE,
потерю сессии и внутренние повторы при сборке проекта.
`ChatContextTest`, `ChatToolsTest`, `ChatMcpTest` и `ChatCommandsTest`
проверяют UI-контракты контекста, изменений, ревью, MCP и команд.
Новая общая телеметрия и новый тестовый фреймворк не добавляются.

## Подготовка одного окружения

Использовать отдельную тестовую рабочую область и проект `Сценарии1С`.
Набор содержит исходники, а не готовую информационную базу и не импортёр
метаданных произвольной версии EDT.

1. В мастере EDT создать пустую конфигурацию `Сценарии1С` без БСП.
   Создать шесть общих модулей с именами каталогов `F/project/src/CommonModules`:
   РасчетыЗаказов, ОформлениеЗаказов, ПодсказкиЗаказов, БуферЗаказов,
   ЗапросыТоваров, ПроверкаЗаказов. У всех `Сервер=Да`,
   `Вызов сервера=Да`, `Глобальный=Нет`, привилегированный режим выключен,
   повторное использование возвращаемых значений выключено, остальные
   клиентские/внешние контексты выключены.
2. Скопировать **только Module.bsl** из `F/project` в соответствующие
   модули. Метаданные оставить созданными EDT. Фиксировать версию платформы,
   режим совместимости и архив исходного тестового проекта с метаданными:
   его UUID и формат зависят от версии EDT. Между сравниваемыми версиями
   плагина использовать один и тот же архив проекта.
3. Сохранить все редакторы, дождаться завершения сборки, получить исходные
   ошибки EDT. Исправление старых ошибок окружения не входит в задачу
   модели. При отсутствии нужной платформы/EDT-MCP отметить соответствующие
   сценарии `not_run`, не заменять их ответами заглушки.
4. Создать локальный git-репозиторий тестового проекта, зафиксировать всё
   исходное состояние. При копировании отключить преобразование строк
   (`core.autocrlf=false`). Ничего не отправлять в remote.
5. Заполнить [configuration-template.json](scenarios/configuration-template.json),
   сохранить фактические схемы/фильтры инструментов и тексты включённых
   навыков. Набор навыков одинаков в сравниваемых конфигурациях; пустой
   список означает, что все отключены. Имена моделей и параметры
   брать из фактического сервера, а не из предположения по названию.

Для обычного файлового проекта без EDT можно подготовить копию так:

```text
python tools/developer_scenarios.py prepare <новый-каталог-проекта>
```

Команда создаёт новый каталог и отказывается перезаписывать существующий.
Для реальной EDT исходники из этой копии переносить в проект из мастера.

## Перед каждым повтором

1. Закрыть редакторы без сохранения результатов прошлого прогона.
   Восстановить отдельную тестовую копию из исходного архива. Не применять
   reset/clean к рабочему проекту владельца.
2. Начать новый чат, убрать все вложения, выставить режим **Агент**,
   точный системный промпт из configuration-template, окно из матрицы,
   ответ максимум 2048 токена, лимит контекста 40000 символов,
   генерацию названий включить. Авторежим выключить, разрешать только
   предусмотренные карточкой MCP-вызовы. Для S14 вместо нового чата
   загрузить фиксированную историю по инструкции ниже.
3. Включить встроенные инструменты. MCP по умолчанию выключен;
   исключения перечислены в карточках S10/S12/S13/S15.
   Изменять этот профиль в ходе сравнения нельзя: это отдельная
   конфигурация, если сравнивается отбор инструментов.
4. Наложить состояние карточки. Для S11/S14 при базовых исходниках:

   ```text
   python tools/developer_scenarios.py state S11 <каталог-проекта>
   ```

   S11 сохраняет единственную правку **после** исходного git-коммита.
   S07 накладывается вручную в буфере, без сохранения.
5. После подготовки состояния и окончания сборки сделать снимок файлов
   **вне** проекта. Один файл на прогон, прежний снимок не перезаписывать:

   ```text
   python tools/developer_scenarios.py snapshot <каталог-проекта> <новый-before.json>
   ```

6. Начать запись запросов и времени, отправить промпт дословно. Не
   добавлять подсказки, не исправлять выбор модели и не менять промпт после
   неудачного повтора. Если модель просит уточнение, не предусмотренное
   карточкой, записать вопрос; ответить `Работай по исходной постановке`
   один раз. Это дополнительный запрос и ожидание человека, не новый прогон.

S14: при закрытой EDT скопировать `F/long-chat.json` под именем
`scenario-long.json` в
`<workspace>/.metadata/.plugins/io.github.hansglorias.edtai.ui/chats/`,
в `current.txt` этого каталога записать `scenario-long`.
Это только отдельный тестовый workspace. После запуска выбрать этот чат,
отправить ровно `/compact`, дождаться окончания, затем второй промпт карточки.
История синтетическая и фиксированная; её старые сообщения не считаются
запросами измеряемой модели. Все новые запросы сжатия и продолжения считаются.
Автоматическое сжатие, если возникнет дополнительно, тоже учитывается.
Исходная подпись уже изменена состоянием S14, округление ещё не изменено.

S13: `python tools/fixture_mcp.py expire`. Добавить сервер `Fixture`
по напечатанному localhost URL, фильтр `fixture_read`.
Первый tools/call возвращает 404 до выполнения: клиент должен заново
инициализировать сессию и повторить транспортный запрос. Маркер
`готово-314` появляется только в успешном результате. Перезапускать
процесс перед каждым повтором; в фазе подготовки инструменты не вызывать.
Заглушка не читает и не меняет проект. Этот сценарий проверяет восстановление
транспорта; повтор решения модели после SERVER/TIMEOUT отдельно покрыт
AgentExecutionTest, его не подменять счётчиком tools/call.

S15: `python tools/fixture_mcp.py wait`, фильтр `fixture_wait`.
При WAITING нажать Стоп в EDT, затем Enter в консоли сервера; дождаться
окончания активности. До второго промпта проверить базовое дерево через
`check S15 ... --stopped`. Не держать ожидание больше 120 секунд.
Если модель записала до первого вызова ожидания, это fail и нарушение порядка.
Если она вообще не дошла до fixture_wait, отметить `cancel_not_exercised`
и не засчитывать отмену как успешную. При уже начавшейся внешней записи Стоп
не гарантирует откат; в данном сценарии до Стоп разрешено только чтение.

## Проверка исходников и diff

```text
python tools/developer_scenarios.py check S05 <каталог-проекта> <before.json>
python tools/developer_scenarios.py check S07 <каталог-проекта> <before.json> --buffer <экспорт-буфера.bsl>
```

Экспорт S07 делать копированием текста документа во внешний файл, не
сохранением исходного редактора. Отдельно записать dirty=true и проверить
Ctrl+Z: возвращается старая подпись, а пользовательские скидка 7 и билет
314 остаются. Откат делать после фиксации результата прогона.

Проверка сравнивает весь снимок файлов (кроме .git), обнаруживает новые
и удалённые файлы, проверяет исходную версию шести модулей, допускает только
указанные изменения. Эталон изменённого BSL сравнивается с нормализацией
LF/CRLF, но BOM и набор разделителей должны остаться прежними. Для
остальных файлов требуется совпадение байтов. Изменения метаданных,
побочные правки и изменения в других файлах — fail.
Снимок с произвольными исходниками нельзя использовать как baseline.

Зелёный файловый oracle — только часть оценки. По карточке проверить трассу:
действительно ли читался исходник, была ли запись, выполнено ли чтение
после неё, вызвана ли справка и report_review. Для S11 проверить в EDT
одну карточку и маркер на строке 7, тип error; файл должен остаться
изменённым пользователем, без исправления моделью. Для S09 по возможности
выполнить validate_query и контроль на таблице значений в тестовой базе;
зафиксировать доступность и результат, не выдавать Java-проверку за проверку 1С.

## Матрица настоящей модели

Для каждой точно закреплённой конфигурации Qwen 7–14B:
15 сценариев × окна **8192, 16384, 32768** × **5 повторов** = **225 прогонов**.
Две модели дают 450; другое квантование, сервер, template или reasoning —
новая конфигурация с собственной матрицей. Размер окна не является
признаком качества модели.

Окно задать и в клиенте, и в сервере; записать фактический лимит обоих.
Закрепить model/revision/hash весов, tokenizer, квантование (включая тип
и размер), сервер/версию/аргументы запуска, точный chat template и tool parser,
reasoning on/off/бюджет, max output, temperature/top-p/top-k и seed.
Если сервер не поддерживает seed или другой параметр, записать это явно;
пять повторов всё равно провести, не называть их детерминированными.

Записать ОС, EDT/Eclipse/Java/платформу/MCP, CPU/RAM, GPU/число/VRAM,
драйвер, offload, потоки, прочую нагрузку. Один измеряемый запрос одновременно.
Разогрев провести заранее отдельной задачей; политику prompt cache,
загрузки/выгрузки модели и прогрева держать одинаковой. Время холодного старта,
если измеряется, публиковать отдельно.
Для сравнения до/после чередовать версии по повтору (AB/BA), сохранять
одинаковый порядок сценариев, seeds и окружение; не менять одновременно
код, модель и профиль инструментов. Отказы по окну и ошибки не выбрасывать.

## Метрики и полная стоимость задачи

Шаблоны: [runs.csv](scenarios/runs.csv), [requests.csv](scenarios/requests.csv),
[tools.csv](scenarios/tools.csv), [human-waits.csv](scenarios/human-waits.csv).
Хранить рядом конфигурацию, точные запросы/ответы локального тестового
сервера, историю чата, снимки до/после, git diff, экспорт буфера и решение
oracle. Не коммитить токены, адреса закрытого контура и сырые журналы владельца.

Каждый физический запрос модели получает request_id. Фаза: `answer`,
`summary_auto`, `summary_manual`, `title` или `unknown`.
Повтор при переполнении окна, отклонении schemas/tools, сетевой ошибке —
отдельная строка с parent_request_id и номером попытки, даже если завершился
без usage. Неизвестная фаза не должна пропасть из общего числа запросов.
Контрольные вызовы оценщика и разогрев записывать отдельно вне задачи.

Для input и output независимо хранить источник `server`, `estimate`
или `unknown`: отсутствие значения — пустая ячейка/null, **не 0**.
Серверные usage не заменять длиной текста, а оценки не складывать с ними
в одно «точное» число. Суммировать каждую известную серверную величину
один раз на физический запрос, отдельно публиковать покрытие N/M запросов
для входа и выхода. При неполном покрытии это известный подытог, не полная
стоимость. Сохранить исходный usage, правила включения cached input,
cache creation/read и reasoning output; не прибавлять их второй раз,
если сервер уже включил их в input/output. Оценки публиковать отдельно
с методом и версией; reasoning, если usage отсутствует, не восстанавливается
по видимому ответу. Пиковый контекст и сумма входа всех запросов — разные метрики.

Источником могут быть полные журналы тестового model server/шлюза и MCP,
сопоставленные по времени и идентификаторам с чатами. Если доступа к ним нет,
точная стоимость и число невидимых попыток — unknown; полнота измерения
`incomplete`. Строка состояния TokenUsage и журнал ToolExecutionLedger
не являются полной телеметрией: они не доказывают учёт сжатия, названия,
ошибок и внутренних транспортных повторов. Этот PR не меняет их API.

Инструменты считать на трёх уровнях: решения модели (logical_call_id),
фактические исполнения и транспортные попытки MCP (включая initialize,
tools/list отдельно от tools/call). Заблокированный дубль и отказ пользователя
не являются исполнениями. Повтор ожидания сборки внутри McpTool и
переподключение McpClient не являются дополнительными решениями модели.
Неопределённый эффект записи записать как `unknown`, не как «не выполнено».

Начало времени задачи — отправка первого промпта; окончание успеха —
завершение всех обязательных проверок oracle, включая файлы, трассу и
доступную проверку EDT. Фоновое название дождаться для окончательного
подсчёта стоимости. Интервалы согласования, ввода оценщика, нажатия
Стоп/Enter и действий проверки человеком записывать отдельно; пересечения
объединять, не складывать дважды. `elapsed_ms` включает ожидание человека,
`active_ms=elapsed_ms−human_wait_ms`. Время до проверенного результата
`time_to_verified_ms` заполняется только для pass; для fail/timeout —
null, при этом реальное затраченное время сохраняется.

Предел одного прогона — 600 с активного времени, ожидания человека — 120 с
на одно действие. Достижение предела даёт timeout; остановить, сохранить
полученные данные и исходники, не подменять повтором. Терминальные статусы:
pass, partial, fail, timeout, blocked_environment, not_run. Недоступность
заранее требуемого EDT-MCP — blocked_environment; отказ/недоступность сервиса
во время подготовленного прогона — fail/timeout, а не исключение из выборки.
