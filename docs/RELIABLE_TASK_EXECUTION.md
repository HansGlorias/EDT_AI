## Реализация пункта 1 и границы

`RepetitionGuard` в core проверяет видимый текст до передачи очередного
фрагмента подписчику. Состояние сохраняется между SSE-событиями; периоды
1–256 символов UTF-16, минимум 16 копий и 512 символов подряд. Повтор
максимального периода останавливается не позже 4096 символов. Детектор
хранит только кольцевое окно и счётчики, а не дополнительную копию ответа.
Проверяется и ответ без SSE; в этом случае тело уже получено от сервера.

Fenced code (обратные кавычки/тильды, включая CRLF и незакрытый блок),
inline code, строки цитаты и код с отступом исключаются. Обычный XML
с разными данными, короткие примеры одинаковых тегов и чистые пробелы
сохраняются. Это эвристика точного непрерывного повтора, не классификатор
качества: переменные/длиннее 256 символов циклы и повтор внутри примера
не обнаруживаются. Скрытое reasoning и JSON аргументов не проверяются.

При срабатывании HTTP body закрывается, запрос заканчивается отдельной
ошибкой `GenerationStoppedException`; автоматического восстановления нет.
Уже показанные части повторяющегося хвоста удаляются при завершении ответа.
В истории остаётся STOPPED с полезным префиксом, выполненными ToolUse,
вложениями и доступной статистикой; причина — отдельной записью ERROR,
которая не передаётся модели. Вызовы испорченного текущего шага не исполняются.
Следующий запрос и история после перезапуска не содержат удалённого хвоста.
Это не очистка ранее сохранённых повреждённых ответов из старых версий.

Тот же механизм работает у читающего специалиста: ведущий получает partial,
очищенный префикс, проверенную область и причину; в панели остаётся полезный
префикс. Расход оборванного запроса без server usage остаётся неизвестным.
Закрытие клиентского соединения не доказывает, что конкретный сервер
немедленно прекратил вычисление или начисление стоимости.

Автотесты: `RepetitionGuardTest`, `GenerationStopTest`, сценарий
`ExploreProjectTest.corruptChildKeepsItsPrefixAndCheckedAreaWithoutRetry`.
Локально — целевые core-проверки; полный Windows/Ubuntu core + UI — CI.
Реальная Qwen и четыре предметных сценария (объяснение подсистемы, правка BSL,
кнопка формы, метаданные) требуют отдельной ручной репетиции на фиксированных
исходниках. Эта задача не добавляет методику изменения формы из пункта 4.
