# Аналитическая выгрузка выбранного чата

Решение 03.11.2026: реализовать, чтобы владелец мог передавать реальные
сценарии работы ИИ/разработчику и разбирать ошибки, задержки и расход.
Это отдельная функция от анонимного DiagnosticLog физических запросов.

Статус этого среза: первый PR в работе в чате
01a19b10-a6a2-7123-8468-acc3291e4d84, worktree 886d; функция ещё не
объявлена выпущенной. Подключение диагностики к физическим запросам
отдельно ведёт агент root. В main `8cff4ca` уже есть вопросы (#89) и
[изолированная разведка](EXPLORE_PROJECT.md) (#90), но их наличие не даёт
полной сохранённой трассы чата. Общая карта — [WORKSTREAMS.md](WORKSTREAMS.md).

## Первый полезный PR

Экспорт ZIP выбранного чата средствами JDK, локально, без отправки:

- manifest.json: версия схемы/плагина, доступные настройки модели без
  endpoint и секретов, полнота и границы записи;
- conversation.md: содержимое при явном выборе пользователя;
- conversation.json или events.jsonl: доступные структурированные
  сообщения/ToolUse, статусы, ошибки, usage с provenance;
- summary.md: измеренные числа и явные unavailable/truncated, не
  предположения о том, что было в незафиксированных запросах;
- feedback.md: что ожидалось, что получилось, замечания пользователя.

По умолчанию метрики без содержимого; выбор включить разговор/код явно
показывается перед сохранением. Полный экспорт может содержать рабочие
данные; он не называется анонимным. API tokens, HTTP headers, Secure
Storage, endpoint не входят ни в один режим; известные секреты очищаются
и из ошибок/текста. Полная очистка произвольного текста не гарантируется.
Весь репозиторий и посторонние чаты не экспортируются.

Существующий Markdown export не хранит полную трассу. Глобальный анонимный
request log сам по себе не даёт проверенной привязки к выбранному чату:
его нельзя целиком приклеить к разговору. Контракт metadata-only журнала —
[LOCAL_DIAGNOSTICS.md](LOCAL_DIAGNOSTICS.md); его подключение пока отдельно
в работе. В первом PR использовать только реально доступные
данные, включая явное указание отсутствующих args/results и timings.

## Следующий PR: запись подробной трассы

До очередной задачи пользователь включает запись подробностей выбранного
чата. Нельзя восстановить полный trace прошлой задачи задним числом.
Ротация/квоты на чат и общий объём, ограниченные payload, явные признаки
обрезки, очистка записи пользователем. Отдельный режим от metadata-only
DiagnosticLog: не ослаблять его прежний запрет на произвольный контент.

Стабильные task/run/parent/request/span ids связывают:

- сообщения и смены режима/модели;
- запросы ведущего, разведчиков, сжатия и названия, повторы и отмены;
- начало/окончание операций, параметры и результаты при разрешённой
  записи содержимого, разрешение/отказ пользователя;
- ошибки с очищенным текстом, факт обрезки, события сжатия;
- изменения/diff при наличии и разрешении записи;
- длительность (уже есть: у ответа `reply_stats` — начало, конец, ожидание,
  рассуждение, текст, инструменты, токены; у вызова `duration_ms`; в сводке —
  время ответов и число заблокированных повторов), первый видимый текст
  отдельно от первого сетевого события,
  очередь/ожидание пользователя отдельно от работы модели;
- input/output SERVER/ESTIMATE/UNKNOWN, размеры запроса отдельно от токенов.

Структура подготовленного запроса (доли истории, правил, инструментов и
результатов) помогает объяснять расход. Точный состав не выводить из одной
суммы байтов. Полные тела запросов не логировать автоматически; если
понадобятся для диагностики — отдельный контролируемый выбор и очистка.

Сумма task включает детей и служебные запросы ровно один раз. Контекст —
свойство конкретного запроса, не сумма всех агентов. UNKNOWN не равен нулю.
Число предложенных tool calls не выдавать за выполненные операции.

## Проверки

ZIP/schema/кириллица, отсутствие секретов в обоих режимах, выбор одного
чата, пустая/старая/обрезанная история, отмена сохранения, неизвестные
метрики. Для trace: корреляция детей, duplicate/late completion, квоты,
остановка, включение в середине задачи и честная отметка неполной записи.
Локально targeted core/UI; полные Windows/Ubuntu проверки в CI.

Первый PR поручен чату 01a19b10-a6a2-7123-8468-acc3291e4d84 (Sol 6.1),
worktree 886d и сейчас выполняется. Полная подробная трасса — бэклог,
в первый PR не входит. Её разработка и другие независимые направления не
требуют предварительного A/B допуска; реальные прогоны нужны для проверки
полезности и стоимости уже работающих функций.
