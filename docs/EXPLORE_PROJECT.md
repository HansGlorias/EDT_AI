# Исследование, ревью и проверка отдельным агентом

`explore_project(question, scope?)` — встроенный инструмент ведущей модели
для широкого поиска и изучения связей между несколькими модулями. Простой
read/search ведущий выполняет сам. Пользователь может написать «исследуй
проект отдельным разведчиком»; решение вызвать инструмент принимает ведущая
модель, отдельного классификатора сложности нет. Качество делегирования на
реальной модели проверяется репетицией, а не fake-server тестами.

`delegate_task(role, task, scope?)` использует тот же механизм и общую квоту:
research — исследование связей, review — ошибки и регрессии по diff/коду,
verify — проверка гипотезы доступной диагностикой. Это роли с разными
инструкциями и подписями прогресса; у всех одинаковая политика только чтения.
Ревью не публикует маркеры и не меняет файлы. Проверяющий не запускает операции
с побочными эффектами: если нужного читающего инструмента нет, сообщает, что
проверка недоступна. Реальное исполнение тестов не подразумевается названием роли.

По подходу [Claude Code Explore](https://code.claude.com/docs/en/sub-agents):
изолированный контекст, ограниченные чтения, один итог ведущему. Это своя
реализация EDT AI, не подключение Claude Code или внешний сервис.

## Возможности

- Отдельный `AgentLoop` с коротким системным промптом. В него передаются
  только question/task и scope, без истории родителя, пользовательского
  системного промпта, ProjectBrief и списка скиллов.
- Те же зафиксированные protocol/endpoint/model/token/TLS/window, что у
  текущего цикла родителя. Другой сервер, fast profile и fallback не выбираются.
- Исходные чтения `ProjectTools` и `GitTools` (если EGit доступен);
  происхождение встроенных инструментов проверяется по реализации.
  MCP берётся из отфильтрованного набора родителя: только с явным
  readOnlyHint=true и без признака записи. Это доверие аннотациям сервера,
  не песочница от сервера, который ложно объявил запись чтением. Все такие
  инструменты доступны в отдельном дочернем каталоге схем по запросу.
  Подтверждение использует обычную политику чата; Stop отменяет ожидание.
  Вопросы пользователю, правки, файлы, save_skill и report_review отсутствуют. Для больших результатов
  внутри ребёнка доступен его локальный `read_tool_result`.
- Глубина ровно 1: у дочернего цикла нет explore_project/delegate_task. Один ребёнок
  одновременно на родительский ответ; вызовы в одном пакете последовательны.
  Не более **2 запусков суммарно для всех ролей и обоих инструментов** на ответ
  и **50 рабочих физических запросов** на ребёнка — столько же рабочих шагов,
  сколько у ведущего. Повторы после переполнения/отказа схемы тоже входят в
  этот счётчик. Есть один резервный запрос текстового итога по найденному:
  не больше 51 запроса суммарно. После исчерпания рабочего лимита новые
  вызовы инструментов не выполняются. В OpenAI описания убираются, в Anthropic
  сохраняются для корректной истории tool_use/tool_result; запрос содержит
  инструкцию дать текстовый итог. Отчёт тогда `partial` с причиной,
  но работа специалиста не пропадает. На 30-м шаге — напоминание переходить
  к итогу, на последнем рабочем — явное требование закончить.
  Лимит выхода дочернего запроса наследуется от родителя без отдельного
  потолка 2048. Автоматический режим также наследуется: OpenAI не получает
  max_tokens, Anthropic получает обычное значение 8192. Явный лимит пользователя
  и серверный предел сохраняются; обрыв по токенам не продолжается скрыто.
  Эти лимиты защитные, не обещание времени выполнения или стоимости.
- question/task — непустая строка до 4000 символов, scope — необязательная строка
  до 1000. Типы, null и лишние поля проверяются до запуска. Scope — ориентир
  для поиска, не новая песочница доступа и не выбор проекта по умолчанию.
- Родитель ждёт completion future. Для polling не делаются запросы модели.
  Прогресс показывается строками «Разведка: …», «Ревью: …», «Проверка: …»; ID содержит
  родительский tool call и отдельный UUID ребёнка. Текст промежуточных
  рассуждений и ответов ребёнка в ленту родителя не стримится.

Остановка отменяет future родителя, прерывает его ожидание, отменяет future
ребёнка и текущий HTTP-запрос ребёнка. Прерывание между вызовами не позволяет
начать следующий. Поздний результат не возобновляет родителя и не публикует
новый дочерний прогресс в завершённый ответ. Как и для других инструментов,
синхронное чтение файлов может завершиться позже, если само чтение не
реагирует на interrupt; новых запросов после отмены не будет.

## Отчёт и проверка фактов

Один текстовый Tool.Result с полным очищенным итогом. Программная оболочка
содержит status, выводы модели, область успешных чтений и оговорку о неизвестном.
Короткий промпт просит модель дать ссылки Модуль:строка и отделить неизвестное;
сложная JSON-схема от слабой модели не требуется. Проверенная область — первые
8 успешных чтений с короткими итогами, не полный аудит проекта. Итог не режется
по прежним порогам 3700/6000 символов. Родитель использует обычный ToolResultStore:
большой отчёт сохраняется целиком и передаётся страницами через read_tool_result.
Бюджет запроса и общий лимит хранения результатов остаются прежними; если
снимок не помещается в хранилище, результат явно обозначает предпросмотр без
продолжения. Это доступность полного отчёта, а не гарантия его чтения моделью.
В истории и карточке специалиста сохраняется полный очищенный текст без
прежней обрезки до 4000 символов. Сама длина отчёта не означает `partial`.

- `complete` — цикл закончил итог без отмеченного сбоя, был хотя бы один
  успешный вызов чтения. Это **не доказательство** истинности текста,
  правильности ссылок или полноты исследования.
- `partial` — достигнут лимит рабочих запросов/шагов, сервер оборвал генерацию
  по токенам, модель зациклилась на повторах, чтения/инструменты дали ошибку,
  сервер отказался от инструментов, нет подтверждённых чтений или итог пустой.
  Причина перечисляется в результате ведущему и начале отчёта в карточке.
- `failed` — нет разрешённых чтений либо запрос завершился ошибкой без итога.
- `cancelled` — отмена в lifecycle/progress. При Stop отчёт не возвращается
  ведущей модели: отменён весь родительский ответ. В ленте незавершённые
  операции получают обычную пометку прерывания.

Область выводится из фактически успешных вызовов, а не из уверений модели.
Просмотр каталога и подключение схем не считаются проверкой проекта.
Ссылки в модельном тексте программно не подтверждаются. Ведущий обязан
перечитать модуль перед правкой. Отчёт не разрешает повторную запись,
не является снимком актуальности и не попадает в журнал фактов как изменение.
Тексты файлов и подробный child transcript остаются у ребёнка. Генерируемые
child snapshot ID и названия протокола дочитывания удаляются из отчёта;
ссылок на недоступные ребёнку/родителю снимки наружу не передаём. При
необходимости сам ограниченный отчёт хранится обычным ToolResultStore
родителя с собственным действительным ID.

## Расход и совместимость

`AgentLoop` хранит накопленный расход родительских запросов отдельно от
накопленных child usage, заменяя обновления одного ребёнка по его ID,
а не складывая cumulative usage повторно. Наружный onUsage получает сумму
input/output с сохранением server/estimate/unknown/mixed происхождения.
Context и его источник остаются от последнего родительского запроса,
включая оценку при отправке; дочернее окно их не подменяет. Последующие
запросы родителя не стирают уже потраченные дочерние токены.
Пока дочерний запрос не завершён, полный расход отмечен unknown. Если запрос
ребёнка оборвался без usage, известные числа прежних шагов сохраняются как
часть расхода с unknown происхождением полного итога, в том числе после
последующего успешного повтора. Их нельзя выдавать за точную полную сумму.

Это учёт внутри ответа, без title/summary. Opt-in JSONL запросов уже доступен
по [LOCAL_DIAGNOSTICS.md](LOCAL_DIAGNOSTICS.md); полная корреляция task/run/child
остаётся следующей работой. Экспорт чата отличает дочерние progress-записи
обоих инструментов от настоящих родительских вызовов. Не обещаем точных
затрат, если сервер не вернул usage прерванного запроса.

Существующий ask_user (PR #89), пользовательские разрешения и режимы чата
не переписываются. Специалисты доступны и в Плане/Вопросах, когда инструменты
включены: она не меняет файлы. AUTO родителя не даёт ребёнку никаких новых
возможностей записи. AUTO влияет на подтверждение разрешённого MCP, но не
расширяет дочерний каталог до пишущих инструментов.

## Проверка

Core fake server: OpenAI/Anthropic, изоляция контекста/модели, запрет
неразрешённых инструментов и рекурсии, provenance встроенных чтений,
лимиты запусков/запросов с резервным итогом для обоих протоколов, наследование
явного/автоматического выхода, завершение после 12 запросов, сохранение длинного
отчёта и дочитывание его хвоста родителем, причины неполного итога, удаление child snapshot ID,
сумма usage и родительский context, ошибка HTTP, отмена и late completion.
Соседние тесты выполнения/снимков защищают прежнюю семантику инструментов.
Дополнительно: роли, общий лимит explore/delegate, читающий MCP по запросу,
отказ в подтверждении, недоступность пишущих/неаннотированных инструментов,
отдельный набор схем и дочерние записи аналитической выгрузки.
UI: вызов из живого чата, дочерний прогресс и итог ведущего, снимок
`explore-project`; штатные инструменты, вопросы и выключение инструментов
проверяются соседними сценариями. Полный CI — Windows и Ubuntu.

Вручную в EDT Windows/Astra: попросить разведать связи нескольких модулей,
увидеть строки прогресса, получить краткий отчёт/итог без правок; остановить
долгое исследование; убедиться, что ответ не возобновился. Затем попросить
исправление и проверить, что ведущий перечитал соответствующий модуль.
Поручить отдельному ревьюеру проверить текущий diff. Затем попросить отдельного
проверяющего прочитать диагностику EDT-MCP: подтвердить вызов либо остановить
ожидание; убедиться, что непроведённые проверки не объявлены выполненными.
Отдельного диспетчера агентов, фонового UI, параллельного fan-out,
возобновления ребёнка после Stop и выбора разных моделей здесь нет.
