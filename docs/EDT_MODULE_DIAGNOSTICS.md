# Диагностика модуля после правки

## Первый этап

После успешного `edit_module` модель получает не только факт изменения,
но и ограниченный снимок доступных диагностик EDT именно этого файла.
`check_module(module, project?)` позволяет перечитать диагностику без
повторной записи. MCP и облачная модель для этого не нужны.

Защита цикла от повторов сохраняется: одинаковый `check_module` в одном
ответе без промежуточной правки повторно не исполняется. Для более позднего
снимка отправьте новую реплику. Цикл не опрашивает EDT платными шагами модели.

Снимок **не подтверждает завершение проверки новой редакции**. Даже пустой
ответ не означает «код проверен, ошибок нет». Сообщения могут относиться к
предыдущему состоянию модуля. Автоматического исправления, сохранения чужих
черновиков, запуска конфигурации или полной пересборки проекта нет.

Ядро получает независимый от Eclipse `ModuleDiagnostics` через
`WorkspaceFiles.diagnostics`. UI читает необязательный сервис EDT через
OSGi/reflection: отсутствие сервиса или несовместимость версии — явное
«диагностика недоступна», а не ошибка уже выполненной правки. В target
platform не добавляются бандлы EDT или сторонние библиотеки.

Состояния: снимок, недоступно, несохранённый текст, текст изменился во время
чтения, время ожидания истекло. До и после чтения сверяется сохранённый текст;
диагностика с диска не выдаётся за проверку несохранённого редактора.
Сбой диагностического сервиса не превращает применённую запись в неудачную:
модели не нужно повторять `edit_module` ради проверки.

Объём: максимум 20 сообщений, текст одного сообщения до 300 символов,
полный отчёт до 6000 символов с обозначением сокращения. Это лимиты символов,
не точные токены. Схема нового инструмента мала; повторное чтение расходует
один вызов инструмента, автоматический снимок после правки — без отдельного
запроса модели. Доступ к сервису ограничен по времени; зависшее чтение не
порождает очередь новых потоков.

## Что установлено при исследовании

На установленной EDT 2026.1.3.25 (Java 17/Eclipse 4.30) проверены сигнатуры
и вызывающий байткод бандлов validation, bm.xtext, bsl.bm и lcore:

- BSL-проверки публикуют маркеры в
  `com._1c.g5.v8.dt.validation.marker.IMarkerManager`, зарегистрированном
  как OSGi service. Обычный `IFile.findMarkers` не заменяет этот контракт.
- `getMarkers(IProject, Object)` принимает ключ файла в виде строки
  `/Project/src/.../Module.bsl`. Это workspace path, не EMF URI с fragment.
- `Marker.getMessage/getSeverity/getCheckId` и
  `StandardExtraInfo.TEXT_LINE.get(Marker)` дают сохранённые данные.
  Разрешение BM-объектов и `getObjectPresentation` не нужны.
- `getMarkers` фиксирует накопленные маркеры в хранилище, но **не ждёт
  завершения валидации**. Событие обновления сообщает только проекты;
  оно не содержит редакцию файла и признак завершения всех проверок.

Через подключённый EDT-MCP подтверждено, что живая EDT возвращает ошибки
BSL с путём и номером строки. Рабочий код пользователя не изменялся.
Новый адаптер EDT AI пользователь проверяет вручную после установки;
автотесты Eclipse с подставным сервисом не доказывают работу во всех версиях EDT.
Совместимость native API на EDT 2024.2/Astra пока не подтверждена.

Первичный источник для сопоставления механизма —
[GetProjectErrorsTool EDT-MCP](https://github.com/DitriXNew/EDT-MCP/blob/master/mcp/bundles/com.ditrix.edt.mcp.server/src/com/ditrix/edt/mcp/server/tools/impl/GetProjectErrorsTool.java).
Код стороннего проекта не переносится в EDT AI.

## Проверить вручную в отдельном тестовом модуле

1. Сохранить модуль с ошибкой вызова; дождаться её в панели проблем EDT.
   Попросить `check_module`: сверить сообщение и строку.
2. Исправить ошибку через `edit_module`. Подтвердить факт правки и наличие
   диагностического отчёта. Сразу после записи допустим старый снимок;
   он не должен называться успешно завершённой проверкой.
3. После обновления панели проблем повторить `check_module`: ошибка исчезла.
4. Оставить несохранённую правку в редакторе: отчёт сообщает, что сохранённые
   маркеры не проверяют этот текст; файл не сохраняется автоматически.
5. Сравнить поведение Windows и Astra. Если сервис не найден, сохранить
   версию EDT и текст статуса, без кода рабочего проекта.

## Следующий этап: подтверждение свежести

Нужен проверенный сигнал завершения BSL-валидации конкретной редакции файла,
а не пауза, отсутствие Eclipse jobs или новый timestamp одного маркера.
До появления этого контракта не вводить состояние «проверено без ошибок».
Затем: снимок до/после с разделением старых и новых проблем, контролируемая
попытка исправления, общий лимит повторов и проверка влияния на соседние модули.
Синтаксическая диагностика не заменяет тестирование поведения конфигурации.
