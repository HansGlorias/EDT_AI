# EDT AI — задание

## Что это и зачем

Плагин для 1C:EDT, который добавляет в IDE чат с языковой моделью и (в
следующих этапах) даёт модели инструменты через MCP. Целевое использование —
в том числе закрытый контур (КСПД): модель доступна по внутреннему адресу,
TLS через корпоративный CA, интернета нет.

Репозиторий публичный: адреса, токены, имена хостов и сертификаты из КСПД
сюда не попадают ни в код, ни в тесты, ни в README.

## Целевые окружения

| Окружение | EDT | Eclipse | ОС / UI |
|---|---|---|---|
| Рабочая машина | 2026.1, 2025.2 | 4.30 (2023-12) | Windows 10/11, win32 |
| КСПД | 2024.2.6 | 4.30 (2023-12) | Astra Linux 1.8, GTK 3 |

Все три версии EDT собраны на Eclipse 4.30, Java 17 (для 2024.2.6 проверено по
логу установки на Astra). Если появится EDT на другом Eclipse, target platform
опускается до него.

В КСПД EDT стоит в `/opt` от root, sudo у пользователя нет. Установка через
Install New Software в пользовательский профиль p2 падает на компоненте 1C:Link
(chmod на отсутствующий nginx), то есть не работает для любого плагина. Поэтому
есть обходной путь без p2: `tools/edtai-user-install.sh`, подробности и что может
исправить администратор — в `docs/install-astra.md`.

## Архитектурные решения

- **Только Eclipse 4.30.** Target platform — релиз 2023-12, собираем
  против него. API новее 4.30 не используем. Нижние границы версий в
  `Require-Bundle` ставим не выше 4.30.
- **Java 17.** `Bundle-RequiredExecutionEnvironment: JavaSE-17`.
- **Без SWT Browser.** На Astra нет гарантированного WebKitGTK, на Windows
  Edge/IE ведут себя по-разному. Весь UI — обычный SWT/JFace.
- **Сертификаты.** Поддерживаем корпоративный CA: системное хранилище ОС
  (на Windows `Windows-ROOT`) плюс дополнительный PEM-файл. Отключить
  проверку сертификатов нельзя.
- **Токен — только в Eclipse Secure Storage.** В обычных preferences и
  логах токена нет.
- **Ядро без UI.** `core` не зависит от SWT/JFace и тестируется headless.
- **Без сторонних библиотек.** Только JDK 17 и то, что есть в платформе
  4.30. В КСПД плагин ставится скриптом `tools/edtai-user-install.sh`: он
  дописывает в `bundles.info` EDT все `plugins/*.jar` из zip, без p2. Чужой
  бандл (gson, Jackson, MCP SDK) может уже быть в EDT в той же или другой
  версии, и разрешить конфликт без p2 некому — сломается только в КСПД.
  Поэтому JSON, разбор SSE, Markdown и клиент MCP пишем сами в `core`, с
  тестами. Новые бандлы плагина (`io.github.hansglorias.edtai.*`) скрипт
  подхватывает сам.
- **HTTP — `java.net.http.HttpClient`** (модуль JDK, OSGi-импорт не нужен),
  HTTP/1.1, прокси — `ProxySelector.getDefault()`. EDT должна работать на
  JRE с модулем `java.net.http` — первый пункт ручной проверки.
- **API самой EDT** (`com._1c.g5…`) в target platform нет. Контекст берём
  через обычный Eclipse API (`ITextEditor`, `IDocument`, `IFile`) и
  структуру каталогов проекта (`src/CommonModules/<Имя>/Module.bsl`).
- **Лента чата — один `StyledText`** со стилями и ссылками-действиями, а не
  виджет на сообщение: одинаково на GTK и win32, выделение через несколько
  сообщений, дешёвый стриминг. Подтверждения вызова инструментов — панелью
  над полем ввода. Цвета — из темы JFace, не зашиты.

## Как проверяем UI

- **Автотесты в живом workbench** без SWTBot: тест обращается к виджетам
  вида напрямую (package-private геттеры).
- **Логика — в `core`.** Всё, что можно проверить без SWT (клиент модели,
  разбор потока, состояние диалога, позже — разбор Markdown в «текст +
  стили»), тестируется headless.
- **Фейковый сервер модели** в тестах: свой HTTP-сервер на `ServerSocket`
  без зависимостей. Отдаёт SSE частями, ошибки, «зависание», HTTPS со
  сгенерированным тестовым сертификатом для `localhost`.
- **Скриншоты под xvfb.** UI-тесты сохраняют PNG вида в
  `tests/*/target/screenshots/`, CI выкладывает их артефактом
  `screenshots-<ОС>` с Ubuntu (GTK 3) и Windows. С эталонами попиксельно не
  сравниваем — шрифты на машинах разные; скриншоты для просмотра глазами
  при ревью, проверки в тестах — по состоянию виджетов.

## Этапы

### Этап 1. Каркас — готово

Вид «EDT AI» с эхо-провайдером, страница настроек (протокол, адрес,
модель, токен в Secure Storage, сертификаты, MCP-серверы), тесты, CI на
Ubuntu и Windows, zip update-site, установка в КСПД скриптом.

### Этап 2. Подключение к модели и стриминг — готово

Чат отвечает настоящей моделью, ответ появляется по мере генерации, запрос
можно остановить, ошибки понятны без чтения логов.

Состав:

1. **JSON** (`core.json`): разбор и запись, без сторонних библиотек.
2. **Клиент модели** (`core.llm`) на `HttpClient` с `SSLContext` из
   настроек:
   - OpenAI-совместимый: `POST …/v1/chat/completions`, `stream: true`,
     `Authorization: Bearer`; конец потока — `[DONE]` или закрытие
     соединения;
   - Anthropic Messages: `POST …/v1/messages`, `x-api-key`,
     `anthropic-version: 2023-06-01`, события `content_block_delta`,
     `message_stop`, `error`;
   - адрес: `https://host`, `https://host/v1` и полный адрес метода
     работают одинаково;
   - пустой токен допустим (локальные Ollama, LM Studio) — заголовок
     авторизации тогда не шлётся;
   - если сервер не стал стримить и вернул обычный JSON — берём ответ из
     него;
   - отмена запроса; таймауты: подключение, начало ответа, простой
     потока (сервер замолчал посреди ответа).
3. **Понятные ошибки** по-русски: хост не найден, соединение отклонено,
   таймауты, сертификату нет доверия (с подсказкой добавить CA), сертификат
   выдан на другое имя или просрочен, http на https-порт, HTTP 400/401/403/
   404/429/5xx с текстом ошибки сервера. Токена нет ни в одном сообщении.
4. **Диалог** (`ChatSession`): ответ растёт по мере стриминга, «Стоп»
   оставляет полученную часть с пометкой «остановлено», «Повторить» после
   ошибки или остановки. Эхо-провайдер — только для тестов.
5. **Вид чата:**
   - текст ответа появляется постепенно (перерисовка не чаще ~25 раз в
     секунду), прокрутка не дёргает, если пользователь читает выше;
   - «Отправить» на время ответа становится «Стоп», Esc в поле ввода —
     тоже стоп;
   - ошибка — своим цветом, со ссылкой «Повторить»;
   - модель не настроена — вместо пустой ленты подсказка и ссылка
     «Открыть настройки»;
   - строка состояния: модель, сервер, что происходит;
   - цвета из темы (читается и в тёмной теме EDT).
   Отправка остаётся по Ctrl+Enter, как принято в Eclipse.
6. **Настройки:**
   - «Макс. токенов ответа» (пусто — по умолчанию: для Anthropic 8192, в
     OpenAI-совместимый не передаётся);
   - кнопка «Проверить подключение»: короткий настоящий запрос с текущими
     значениями полей, результат на странице;
   - предупреждение, если токен уйдёт по `http://` не на localhost.
7. **Тесты:**
   - `core`: JSON, разбор SSE (в том числе событие, разрезанное между
     пакетами), оба протокола против фейкового сервера, ответ без
     стриминга, отмена, таймаут простоя, ошибки HTTP и сети, HTTPS с
     тестовым CA (доверяем / не доверяем / чужое имя), токен не попадает
     в тексты ошибок, нормализация адреса, новые настройки;
   - UI: вид без настроек показывает подсказку; с настройками на фейковый
     сервер — ответ стримится в ленту, «Стоп» останавливает, ошибка
     показывается с «Повторить»; скриншоты этих состояний.

Критерии готовности:

- `./mvnw -B verify` зелёный локально и в CI на обеих ОС, скриншоты в
  артефактах;
- в EDT на Windows чат отвечает реальной моделью по OpenAI-совместимому
  протоколу (например, локальная Ollama или LM Studio) и по Anthropic;
- в КСПД на Astra чат отвечает внутренней моделью по https с корпоративным
  CA из PEM-файла.

### Этап 3. UI/UX ленты чата — готово

Ответы модели читаются как документ, код из ответа берётся одним щелчком,
диалог не теряется при перезапуске.

Состав:

1. **Markdown** (`core.markdown`): разбор подмножества в «текст + стили»,
   UI только применяет стили к `StyledText`.
   - Блоки: заголовки `#`, абзацы с сохранением переводов строк, списки
     (`-`, `*`, `1.`, вложенные, `[ ]`/`[x]`), цитаты `>`, разделитель
     `---`, таблицы (моноширинно, колонки выровнены), блоки кода ``` и ~~~
     с языком.
   - Внутри строки: `**жирный**`, `*курсив*`, `_курсив_` (только на
     границе слова — `имя_переменной` не трогаем), `~~зачёркнутый~~`,
     `` `код` ``, `[текст](url)`, `<url>` и голые `http(s)://…`, экранирование
     `\*`.
   - Незакрытый блок кода во время стриминга показывается как код до конца
     текста.
2. **Блоки кода:** шрифт редактора (`JFaceResources.TEXT_FONT`), фон на всю
   ширину ленты, над кодом строка с языком и ссылками «Копировать» и
   «Вставить в редактор». Вставка заменяет выделение в активном текстовом
   редакторе (в том числе модуль BSL) и отменяется через Ctrl+Z; если
   редактора нет или он только для чтения — сообщение в строке состояния.
3. **Ссылки** открываются во внешнем браузере через браузер Eclipse
   (`IWorkbenchBrowserSupport`), только `http`, `https`, `mailto`.
4. **Вид ленты как в мессенджерах:** без подписей «Вы» / «Ассистент»;
   своё сообщение — пузырём справа (по ширине текста, не шире 80 % ленты,
   длинный текст переносится внутри), ответ — слева во всю ширину. Под
   сообщением строка с временем и действиями-значками (подпись — во
   всплывающей подсказке):
   - ответ: «Копировать» (исходный Markdown), у последнего — «Повторить»;
   - своё сообщение: «Изменить» — текст возвращается в поле ввода, это
     сообщение и всё после него убираются;
   - ошибка: «Повторить».
   Контекстное меню ленты: «Копировать», «Выделить всё», «Новый чат».
5. **Поле ввода:** Enter — отправить, Shift+Enter — новая строка, Ctrl+Enter
   — тоже отправить. Поле растёт по тексту от 2 до 10 строк. ↑ / ↓ в пустом
   поле — предыдущие отправленные сообщения.
6. **«Новый чат»** на панели вида вместо «Очистить историю». Текущий диалог
   сохраняется в `<рабочая область>/.metadata/.plugins/io.github.hansglorias.edtai.ui/chat.json`
   и восстанавливается при открытии вида; оборванный ответ восстанавливается
   как «остановлено».
7. **Системный промпт** в настройках: многострочное поле, по умолчанию —
   короткий промпт про 1С:Предприятие и EDT. Пустое поле — без системного
   промпта. OpenAI-совместимый — сообщение `system`, Anthropic — поле
   `system`.
8. **Тесты:**
   - `core`: Markdown (каждая конструкция, вложенность, незакрытые
     разметка и блок кода, таблицы, `_` внутри слов, ссылки), слияние стилей
     в непересекающиеся отрезки, кодек и файл истории, `editFrom`, повтор
     готового ответа, системный промпт в обоих протоколах, хранение промпта;
   - UI: ответ с Markdown — стили на месте (жирный, код моноширинным, фон
     блока кода), «Копировать» кладёт код в буфер, «Вставить в редактор»
     меняет текст в открытом редакторе и отменяется, «Изменить», Enter /
     Shift+Enter, ↑ в пустом поле, восстановление диалога после повторного
     открытия вида, «Новый чат»; скриншоты, в том числе узкий вид.

Критерии готовности:

- `./mvnw -B verify` зелёный локально и в CI на обеих ОС, скриншоты в
  артефактах;
- в EDT на Windows и на Astra ответ с кодом BSL читается: код
  моноширинный на фоне, «Вставить в редактор» вставляет в модуль, Ctrl+Z
  отменяет; диалог переживает перезапуск EDT.

### Этап 4. Контекст EDT — сделано, ждёт ручной проверки

Код из EDT попадает в вопрос без копирования: выделил фрагмент в модуле —
спросил о нём; модель видит код и знает, из какого он объекта метаданных.

API EDT нет, поэтому «объект метаданных» выводим из пути файла в формате
проекта EDT: `src/<Тип>/<Имя>/…/<Модуль>.bsl`. Вся логика путей, методов
BSL и сборки текста для модели — в `core` (пакет `core.context`), UI только
берёт выделение и файл из редактора.

Состав:

1. **Имя объекта по пути** (`core.context.BslModulePath`): путь модуля
   относительно проекта ↔ имя в нотации 1С.
   - Объекты верхнего уровня: `CommonModules` → «ОбщийМодуль»,
     `Catalogs` → «Справочник», `Documents` → «Документ», регистры
     сведений, накопления, бухгалтерии, расчёта, обработки, отчёты,
     перечисления, планы видов характеристик, счетов, видов расчёта, обмена,
     бизнес-процессы, задачи, константы, журналы документов, общие формы и
     команды, HTTP- и Web-сервисы, хранилища настроек, критерии отбора.
   - Модули: `Module.bsl` → «Модуль», `ObjectModule.bsl` → «МодульОбъекта»,
     `ManagerModule.bsl` → «МодульМенеджера», `RecordSetModule.bsl` →
     «МодульНабораЗаписей», `ValueManagerModule.bsl` →
     «МодульМенеджераЗначения», `CommandModule.bsl` → «МодульКоманды».
   - Вложенные: `Forms/<Форма>/Module.bsl` →
     «Справочник.Номенклатура.Форма.ФормаЭлемента.Модуль»,
     `Commands/<Команда>/CommandModule.bsl` → «….Команда.<Имя>.МодульКоманды».
   - Модули конфигурации: `src/Configuration/SessionModule.bsl` →
     «Конфигурация.МодульСеанса», а также модули управляемого и обычного
     приложения и внешнего соединения.
   - Обратно: «ОбщийМодуль.ОбщегоНазначения» и
     «Справочник.Номенклатура.МодульОбъекта» → путь файла; имя типа
     принимается и по-английски (`CommonModule.ОбщегоНазначения`), регистр
     не важен.
   - Незнакомый путь — подпись по пути файла, без имени объекта.
2. **Метод под курсором** (`core.context.BslMethods`): границы
   `Процедура`/`Функция` … `КонецПроцедуры`/`КонецФункции` (и английские
   `Procedure`/`Function`), вместе с аннотациями `&НаКлиенте`, `&НаСервере`
   и комментарием над методом, `Асинх`/`Async`. Слова внутри строк и
   комментариев не считаются.
3. **Фрагмент контекста** (`core.context.ContextItem`): проект, путь,
   имя объекта (если узнали), строки «с–по» (или весь модуль), язык, текст.
   Сохраняется в сообщении (`ChatMessage.context`) и в `chat.json` (поле
   необязательное, старые файлы читаются), поэтому «Повторить» и
   перезапуск EDT отправляют тот же код.
4. **Текст для модели** (`core.context.ContextPrompt`): вопрос пользователя,
   а перед ним — каждый фрагмент с заголовком
   «Справочник.Номенклатура.МодульОбъекта (src/Catalogs/Номенклатура/ObjectModule.bsl),
   строки 10–25» и кодом в блоке ```` ```bsl ````; ограждение длиннее любой
   последовательности обратных кавычек внутри кода. Так собирается текст
   сообщения пользователя в обоих протоколах; в ленте показывается только
   вопрос и подписи фрагментов.
   - Лимит: настройка «Лимит контекста, символов» (по умолчанию 40 000) на
     всё сообщение. Что не влезло — обрезается по строкам с пометкой для
     модели «(обрезано: строки 10–400 из 1200)», в подписи фрагмента в UI —
     «обрезано».
5. **«Спросить AI о выделенном»** — команда с горячей клавишей
   Ctrl+Alt+A (меняется в «Окно → Параметры → Общие → Клавиши») и пунктом
   в контекстном меню текстового редактора (`#TextEditorContext`, его же
   использует BSL-редактор EDT на Xtext). Работает и в многостраничном
   редакторе объекта EDT, на странице модуля.
   - Есть выделение — прикрепляет выделенные строки (строки целиком, чтобы
     модель видела отступы и начало конструкции).
   - Нет выделения — метод под курсором; курсор вне метода — весь модуль.
   - Открывает вид «EDT AI», добавляет фрагмент над полем ввода и ставит
     фокус в поле: вопрос пишет пользователь, сразу ничего не отправляется.
   - Тот же фрагмент второй раз не добавляется.
6. **Панель контекста над полем ввода:** фрагменты в ряд, переносятся
   при узком виде: «ОбщийМодуль.ОбщегоНазначения.Модуль: 10–25» ссылкой —
   открывает файл и выделяет эти строки, подсказка — полный путь и размер,
   и «✕» — убрать. Панели нет, когда фрагментов нет. Пункт «+» →
   «Сослаться на модуль проекта…» — диалог поиска модулей рабочей области
   (`FilteredItemsSelectionDialog`) по имени объекта по-русски
   («Номенклатура», «ОбщМод») и по пути. Текст фрагмента берётся в момент
   отправки: из открытого редактора, если файл открыт (с несохранёнными
   правками), иначе из файла; строки выделения отслеживаются через
   `Position` документа и не сбиваются от правок выше. После отправки
   панель очищается.
7. **Фрагменты в ленте:** в начале своего сообщения — строка «Контекст:» с
   подписями фрагментов ссылками (открыть файл на этих строках; если файла
   уже нет — сообщение в строке состояния). «Изменить» возвращает в поле
   ввода и текст, и фрагменты.
8. **Вставка в редактор** (заменяет выделение, отменяется Ctrl+Z — сделано
   в этапе 3) дополнительно: переводы строк — как в документе, вторая и
   следующие строки кода получают отступ строки, куда вставляем
   (`core.context.CodeInsertion`).
9. **Тесты:**
   - `core`: путь ↔ имя для каждого вида модуля, формы, команды, модули
     конфигурации, английские имена типов, незнакомые пути; метод под
     курсором (аннотации, комментарий над методом, `Асинх`, ключевые слова
     в строках и комментариях, курсор между методами, незакрытый метод);
     сборка текста для модели (ограждение, несколько фрагментов, обрезка по
     лимиту с пометкой); кодек `chat.json` с фрагментами и без (старый
     файл); оба протокола против фейкового сервера — код и путь в теле
     запроса; `editFrom` и «Повторить» с фрагментами; отступы и переводы
     строк при вставке; новая настройка.
   - UI: проект с `src/CommonModules/Тест/Module.bsl` в редакторе —
     команда с выделением, без выделения (метод), вне метода (модуль) даёт
     фрагмент на панели с верной подписью; повтор не дублирует; «✕»
     убирает; ссылка фрагмента выделяет строки в редакторе; правка выше
     выделения не сбивает строки; отправка — фейковый сервер получил код,
     в ленте строка «Контекст:», панель пуста; «Изменить» возвращает
     фрагменты; восстановление после повторного открытия вида; пункт есть в
     контекстном меню редактора и у команды есть привязка Ctrl+Alt+A;
     поиск модуля в диалоге по русскому имени; вставка с отступом и Ctrl+Z;
     скриншоты: панель контекста, лента с контекстом, узкий вид.

Решения, принятые при реализации:

- Фрагмент — снимок в сообщении: в `chat.json` лежит код, который ушёл
  модели, поэтому «Повторить» и перезапуск не зависят от того, что стало с
  файлом. До отправки на панели — ссылка на файл и строки, текст снимается
  в момент отправки.
- Текст открытого файла берётся из file buffer Eclipse
  (`ITextFileBufferManager`) — тот же документ, что у редактора, с
  несохранёнными правками; закрытый файл читается с диска в его кодировке,
  BOM отбрасывается.
- Выделение «до начала следующей строки» (как при выделении строк мышью
  слева) — строки выше неё, следующая не прикрепляется.
- Метод под курсором включает аннотации и комментарий непосредственно над
  ним (без пустой строки между); `#Область` не включается.
- Лимит считается по тексту кода; заголовки фрагментов и вопрос в него не
  входят. Фрагменты обрезаются по порядку: первые прикреплённые целее.
- Без текста вопроса отправить нельзя, даже с фрагментами: вопрос задаёт,
  что делать с кодом.
- Пустой поиск в «Прикрепить модуль…» показывает все `.bsl` открытых
  проектов; служебные каталоги (`.settings`, производные) не обходятся.
- В CI на Linux явно задана локаль `C.UTF-8`: без неё JVM не создаёт
  каталоги с кириллицей (`src/CommonModules/Тест`) в UI-тестах.

Спорные места — проверить в EDT или обсудить:

- **Подменю «EDT AI» редактора** (`#TextEditorContext`, `<menu>`):
  «Спросить о выделенном» и команды `explainSelection`, `reviewSelection`,
  `refactorSelection` (`CodeActionHandler`): фрагмент как у Ctrl+Alt+A и
  готовый вопрос (`EXPLAIN_PROMPT`, `REVIEW_CODE_PROMPT`,
  `REFACTOR_PROMPT`) — сразу модели вместе с уже прикреплённым, во время
  ответа — в очередь (`ChatView.askAboutCode`).
- **Кнопка в окне коммита EGit**: вклад в `toolbar:org.eclipse.egit.ui.StagingView`
  без зависимости от EGit (нет вида — нет кнопки), команда `commitMessage`
  (`CommitMessageHandler`). Поле сообщения — первое редактируемое
  многострочное `StyledText` вида (виджет части через `MPart`,
  `org.eclipse.e4.ui.model.workbench`). Чат показывается, не забирая
  фокус; вопрос `COMMIT_PROMPT`, когда ответ готов (`DONE`), текст первого
  блока кода (`core.chat.CommitMessage`, без блока — ответ целиком) —
  в поле. Во время другого ответа — подсказка нажать позже.
- **Пункт в контекстном меню BSL-редактора.** Вклад в `#TextEditorContext`;
  если EDT регистрирует меню модуля под своим id, пункта не будет (горячая
  клавиша и вид работают). Первый пункт ручной проверки; если не появится —
  добавить второй `menuContribution` с id меню из EDT (если в EDT есть
  PDE, его покажет Menu Spy: Alt+Shift+F2 и щелчок по пункту меню).
- **Ctrl+Alt+A привязана в контексте окна** (`org.eclipse.ui.contexts.window`),
  а не текстового редактора: многостраничный редактор объекта EDT может не
  включать контекст редактора у страницы модуля. Плата — сочетание занято
  во всём окне; если в EDT или в оконном менеджере Astra (Fly) оно уже
  занято, будет конфликт — проверить руками.
- **Имя объекта — по пути файла.** Для нестандартной раскладки (не
  `src/<Тип>/<Имя>/…`) подпись будет путём файла, без имени объекта.
- **Методы ищутся по тексту**, без парсера BSL: препроцессор (`#Если`)
  внутри метода не мешает, но метод, объявленный внутри `#Если … #КонецЕсли`
  с разными сигнатурами в ветках, будет найден как два метода.

Не входит (позже или никогда): структура метаданных из `.mdo`, выделение
в навигаторе EDT (там объекты EDT, а не файлы), автоматическое
прикрепление текущего модуля, чтение модулей моделью по запросу (это
инструменты, этап 5).

Критерии готовности:

- `./mvnw -B verify` зелёный локально и в CI на обеих ОС, скриншоты в
  артефактах;
- в EDT на Windows и на Astra: выделил строки в модуле BSL → Ctrl+Alt+A
  или пункт меню → фрагмент с именем объекта над полем ввода → ответ модели
  про этот код; без выделения прикрепляется метод под курсором; «Прикрепить
  модуль…» находит модуль по русскому имени; диалог с фрагментами переживает
  перезапуск EDT.

### Этап 5. Инструменты (текущий; MVP сделан)

Модель сама смотрит проект: на «что это за конфигурация» или «где
вызывается Х» она вызывает инструменты чтения, а не просит прислать код.

**MVP (сделано):**

1. **Вызов инструментов в обоих протоколах** (`core.llm`), со стримингом:
   OpenAI-совместимый — `tools`, `delta.tool_calls` с аргументами кусками,
   ответ `role: tool`; Anthropic — `tools`, `tool_use` с
   `input_json_delta`, ответ `tool_result`. Ответ без стриминга тоже.
2. **Цикл агента** (`AgentLoop`): запрос → вызовы → результаты → запрос …
   до текстового ответа, не больше 10 шагов подряд; текст всех шагов —
   один ответ; «Стоп» прерывает и запрос, и инструмент.
3. **Встроенные инструменты только на чтение** (`core.tools.ProjectTools`)
   по структуре каталогов проекта, без API EDT:
   - `project_info` — имя, синоним, версия, поставщик, режим
     совместимости, расширение ли (из `Configuration.mdo`, разбор
     `javax.xml` из JDK без DOCTYPE), сколько объектов каждого типа,
     другие проекты рабочей области;
   - `list_objects` — сколько объектов по типам или имена объектов типа
     (с фильтром);
   - `read_module` — модуль по имени 1С или пути, с номерами строк,
     частями по `first_line`/`last_line`; если модуля нет — какие модули
     есть у объекта; несохранённые правки из редактора видны;
   - `search_code` — поиск подстроки без учёта регистра по `.bsl`, с
     фильтром по типу.
   Проект по умолчанию — проект активного редактора, иначе проект с
   `Configuration.mdo`. Объём результата — не больше лимита контекста.
4. **Лента:** под заголовком ответа — строки «→ Читает модуль Х — строки
   1–120 из 120», ошибка — своим цветом. Сохраняются в `chat.json`;
   незавершённый вызов при «Стоп» или перезапуске — «прервано».
5. **Настройка «Инструменты»** (по умолчанию включена). Если сервер
   отклоняет запрос с `tools` (HTTP 400/422 с «tool» в тексте — так
   отвечает vLLM без `--enable-auto-tool-choice`), запрос повторяется без
   инструментов, в ленте об этом строка, и этому серверу (адрес и модель)
   инструменты до перезапуска больше не передаются.
6. **Тесты:** `core` — оба протокола со стримингом вызовов и без, ошибки
   инструментов и кривой JSON аргументов уходят модели, лимит шагов,
   откат без инструментов, каждый инструмент на временном проекте,
   `Configuration.mdo` (в том числе расширение и запрет DOCTYPE), вызовы в
   сообщении и в `chat.json`, настройка; UI — модель читает модуль через
   `read_module`, результат в запросе, строка в ленте, восстановление;
   выключенные инструменты не передаются.

Решения и спорные места MVP:

- **Подтверждения нет.** Инструменты только читают проект, поэтому
  разрешение — флажок в настройках. Панель «Разрешить / Разрешать в этом
  чате / Отклонить» — вместе с инструментами записи. Если в КСПД нужно
  подтверждать и чтение (код уходит модели) — сделать раньше.
- **Вызовы и результаты не входят в историю для следующих вопросов:**
  модель видит только свои итоговые ответы и при следующем вопросе читает
  модуль заново. Проще и не раздувает контекст; цена — повторные вызовы.
- **`search_code` читает файлы с диска,** несохранённые правки не видит
  (`read_module` видит). Поиск по всей типовой конфигурации может занять
  секунды.
- Разметку `Configuration.mdo` проверить на реальных проектах EDT
  2024.2–2026.1.

**Осталось по этапу:**

- ~~Панель подтверждения вызова над полем ввода~~ — сделана в этапе 6 для
  инструментов MCP-серверов.
- Инструменты записи с показом изменений через `org.eclipse.compare`.
- Ссылки из строк вызовов в ленте (открыть прочитанный модуль).

### Этап 6. MCP (текущий; MVP сделан)

Модель вызывает инструменты MCP-серверов из настроек — в первую очередь
EDT-MCP (DitriXNew/EDT-MCP), MCP-сервер внутри самой EDT: ошибки
проекта, метаданные, модули, поиск ссылок, запуск тестов.

**MVP (сделано):**

1. **Клиент MCP по Streamable HTTP** (`core.mcp.McpClient`), JSON-RPC 2.0
   без библиотек: `initialize` (предлагаем протокол `2025-06-18`, дальше —
   версия сервера в `MCP-Protocol-Version`) → `notifications/initialized` →
   `tools/list` (все страницы по `nextCursor`) → `tools/call`. Ответ — JSON
   или SSE (уведомления сервера в потоке пропускаются). Сессия —
   `Mcp-Session-Id`; на HTTP 404 (сервер перезапущен) — новое подключение и
   повтор запроса. Локальный адрес — без прокси, https — с сертификатами из
   настроек. Таймаут вызова — 3 минуты (задачи EDT-MCP бывают долгими).
2. **Результат вызова** — `structuredContent` как JSON, затем самостоятельные
   текстовые части и текст встроенных ресурсов (EDT-MCP отвечает Markdown
   в `resource`). Текст-заглушка не вытесняет структуру; целый блок,
   совпадающий с JSON или его строковым `report`, не дублируется. Поле
   `report` идёт после остальных полей структуры, чтобы большой отчёт
   не вытеснял сведения о фоновой операции при обрезке. Вместо картинок
   и двоичных данных — пометка. Верхнеуровневый `isError` — ошибка
   инструмента, уходит модели вместе с данными. Вложенные ошибки и
   `success=false` сохраняются без общей трактовки; `jobId` и признаки
   незавершённости передаются как данные, а ответ MCP сам по себе не
   подтверждает завершение фоновой операции. Объём ограничен лимитом
   контекста с явной пометкой об обрезке. Условия повторов при сборке
   проекта проверяются по прежнему представлению ответа.
3. **Реестр** (`McpHub`): инструменты включённых серверов вместе со
   встроенными; подключение и список инструментов запоминаются до
   изменения настроек. Имя для модели — как на сервере, при совпадении — с
   префиксом из латиницы имени сервера (`EDT__get_edt_version`) или
   `mcp__`. Сервер, который не подключился, ответ не ломает: в ленте
   строки нет, а красная точка на кнопке MCP у поля ввода (см. ниже).
4. **Фильтр инструментов сервера** в настройках: имена через запятую, `*`
   в конце — по началу имени; пусто — все. У EDT-MCP около сотни
   инструментов, их описания раздувают каждый запрос.
5. **Подтверждение каждого вызова MCP** панелью над полем ввода:
   «Разрешить», «Разрешать в этом чате» (до «Нового чата»), «Отклонить» —
   модель получает «пользователь отклонил вызов». В ленте строка «ждёт
   разрешения», «Стоп» снимает вопрос. Встроенные инструменты — без
   подтверждения (только чтение).
6. **Настройки:** транспорт по умолчанию — http, подсказка
   `http://localhost:8765/mcp`; колонка «Инструменты»; кнопка
   «Проверить» — подключение, имя и версия сервера, сколько инструментов и
   сколько из них пройдут фильтр, предупреждение, если их больше 30.
7. **Тесты:** `core` — фейковый MCP-сервер на `ServerSocket`: подключение,
   постраничный список, вызов, ответы JSON и SSE, истёкшая сессия, ошибки
   JSON-RPC и `isError`, обрезка результата, фильтр и совпадение имён,
   недоступный сервер и stdio — строкой, «Проверить», разбор частей
   результата; цикл агента с подтверждением (отказ, разрешение) и строкой о
   неподключённом сервере; кодек настроек со старыми записями. UI — модель
   вызывает инструмент MCP: панель, «Разрешить» → вызов на сервере и
   результат модели; «Отклонить» → вызова нет; «Разрешать в этом чате» →
   второй раз без вопроса; «Стоп» снимает вопрос; недоступный сервер не
   ломает ответ. Скриншоты `mcp-approval`, `mcp-answer`.

Решения и спорные места:

- **stdio не сделан:** EDT-MCP работает по HTTP, а stdio в КСПД упирается
  в `noexec` домашнего каталога. Запись stdio в настройках — строкой «пока
  не поддерживается» в ленте.
- **Токен MCP-сервера не поддержан.** EDT-MCP без токена слушает только
  127.0.0.1 — для локальной работы хватает. Для удалённого сервера с
  токеном нужен ещё один секрет в Secure Storage.
- **Подтверждение — на каждый вызов MCP**, даже читающий: отличить чтение
  от записи по описанию нельзя. EDT-MCP сам спрашивает перед
  разрушающими операциями; наше подтверждение — раньше и для всех.
- **EDT-MCP и версии EDT:** текущие сборки EDT-MCP — для EDT 2026.1+,
  для 2025.x — версии до 1.26.1; для 2024.2.6 (КСПД) — проверить, скорее
  всего не работает.
- Уведомление `tools/list_changed` не слушаем: список обновляется после
  изменения настроек или перезапуска вида.

**Осталось по этапу:**

- stdio (через интерпретатор: `python3 server.py`) и токен сервера.
- Состояние серверов в виде чата (не только «Проверить» в настройках).
- Обновление списка инструментов по `notifications/tools/list_changed`.

### Этап 7. Доработки по ревью (текущий)

Список с приоритетами — [docs/REVIEW.md](docs/REVIEW.md). Каждый пункт —
отдельным PR, порядок — таблица в конце документа.

- **PR 1 — подтверждение и MCP (сделано):** смена настроек во время
  вызова MCP больше не вешает EDT (`McpClient.close()` не ждёт вызова,
  переподключение в фоне и только при изменении MCP-серверов или
  сертификатов); панель подтверждения не забирает фокус из редактора,
  помечает вкладку вида, в строке состояния «ждёт вашего решения», Esc —
  «Отклонить», пустые аргументы не показываются.
- **PR 2 — бюджет запроса (сделано):** настройка «Окно модели, токенов»
  (по умолчанию 32768). Запрос оценивается по символам (3 на токен) с
  запасом на ответ; если не помещается — сначала вместо результатов
  старых шагов цикла пометка «не передан, вызови снова», потом без кода,
  прикреплённого к старым сообщениям, потом без самых старых обменов;
  последний вопрос остаётся всегда, в ленте строка «Окно модели — …».
  Ошибка переполнения от сервера (OpenAI, vLLM, Anthropic, llama.cpp)
  объясняется по-русски и не считается отказом от инструментов. В
  истории у ответа — короткий след вызванных инструментов
  («[Вызванные инструменты: …]»), сами результаты по-прежнему не входят.
  Спорно: след в истории слабая модель может начать повторять в своих
  ответах — проверить на моделях КСПД.
- **PR 3 — среда проекта в промпте (сделано):** к системному промпту
  перед каждым ответом добавляются сведения о проекте (`ProjectBrief`):
  проект, конфигурация (имя, синоним, версия, режим совместимости — из
  `Configuration.mdo`, разбор запоминается до изменения файла), открытый
  модуль и метод под курсором. Если даны инструменты — ещё правила
  работы с ними («сначала прочитай, не выдумывай имена, ссылайся
  Модуль:строка, не повторяй вызов»). Это отдельно от промпта из
  настроек: правка промпта их не теряет. Повтор вызова с теми же
  аргументами в одном ответе не выполняется — модель получает «результат
  выше»; если результат шага был убран по окну модели, повтор разрешён.
- **PR 4 — рассуждающие модели и оборванный ответ (сделано):** блоки
  `<think>…</think>` в тексте ответа (Qwen3, DeepSeek-R1 через Ollama, LM
  Studio, vLLM без reasoning-parser) не показываются в ленте и не уходят
  в историю, в том числе когда тег разрезан между частями потока; одинокий
  `</think>` (открывающий подставил шаблон сервера) — всё до него
  рассуждение, при стриминге оно видно до конца ответа, потом заменяется
  чистым текстом. `reasoning_content` и блоки thinking Anthropic и раньше
  не показывались; таймаут простоя они продлевают. Ответ, оборванный по
  `max_tokens` (`finish_reason: length`, `stop_reason: max_tokens`), —
  с пометкой в конце и советом. Индикатора «думает…» пока нет: в строке
  состояния «генерирует ответ…».
- **PR 5 — откат без инструментов и `search_code` (сделано):** если
  сервер отклонил первый запрос из-за инструментов, сначала повтор без
  инструментов MCP (часто виновата схема одного из них; признак — нужно
  подтверждение), строка «Инструменты MCP — сервер модели не принял их
  описания…» с текстом сервера; только если и встроенные отклонены —
  без инструментов, и тогда сервер запоминается. Запомненные отказы
  забываются при изменении настроек. `search_code` видит несохранённые
  правки открытых модулей (как `read_module`), нечитаемый файл
  пропускается и считается в итоге, а не роняет поиск.
- **PR 6 — настройки (сделано):** токен — сразу под адресом; у поля
  «Модель» кнопка «Список…» — модели сервера (`GET /v1/models`, заголовки
  авторизации по протоколу) в меню. Ошибка с некорректным токеном
  редактируется и не выдаёт его. README и CLAUDE.md — про окно модели и
  локальную сборку. Что осталось из ревью — раздел «Статус» в
  docs/REVIEW.md.

### Этап 8. Git и правка файлов (текущий)

Решения:

- **Git — через JGit**, который есть в EDT (EGit): работает одинаково на
  Windows и Astra, программа `git` не нужна (в КСПД её может не быть, а
  домашний каталог — `noexec`). Это не сторонняя библиотека: в target
  platform добавлен `org.eclipse.jgit` из того же релиза Eclipse 2023-12,
  в манифесте — `Import-Package` версий `[6, 8)` с
  `resolution:=optional`: если в сборке EDT нет EGit, плагин работает
  без инструментов git.
- Модели — только чтение git; коммиты, ветки и push делает человек в
  EGit.
- **Правка файлов моделью — разрешена** (решение владельца): модель меняет
  модули сама, без подтверждения каждой правки; что изменено, видно в
  диффе (git, «Ревью моих изменений»), как при работе с Claude Code.
  Только `.bsl`, через документ редактора (Ctrl+Z, проверка EDT,
  сохранение — за человеком). Метаданные (`.mdo`) не трогаем.

**Сделано:**

- `core.tools.GitTools`: `git_status` (ветка, последний коммит,
  изменённые / новые / удалённые / конфликты, с именами 1С), `git_diff`
  (незакоммиченные изменения рабочей копии относительно HEAD или
  изменения коммита; по всему проекту или модулю; кириллица в путях без
  кодов; обрезка по лимиту), `git_log` (история проекта или модуля).
  Проект может лежать в подкаталоге репозитория. Видят сохранённые файлы.
- Меню вида чата: «Ревью моих изменений», «Сообщение коммита» — готовые
  вопросы, модель сама вызывает инструменты git.

- `core.tools.EditTools`: `edit_module` — замена единственного вхождения
  точного фрагмента (`TextChange.replace`, переводы строк — как в файле,
  BOM сохраняется). В EDT — через буфер документа (`ITextFileBuffer`):
  видно в открытом редакторе, Ctrl+Z; файл без несохранённых правок
  пользователя сохраняется сразу (виден в git diff), с ними — остаётся
  несохранённым. Только `.bsl` внутри проекта, новые модули не создаются.
  До обращения к правке проверяются обязательные строковые `module`,
  `old_text`, `new_text`: отсутствие, `null` или другой тип — ошибка
  аргументов с именем поля, файл и буфер не меняются. `module` не может
  быть пустым/пробельным, `old_text` — пустым. Явное `new_text=""` удаляет
  фрагмент; пробелы и переводы строк обоих фрагментов не обрезаются.
  В правилах системного промпта: менять код, только когда просят.
  Спорно: без подтверждения — по решению владельца; если в КСПД нужно
  подтверждение, `needsApproval()` у инструмента включает панель.

**Осталось:** «Ревью» с выбором диапазона
(ветка против main), git для нескольких репозиториев в рабочей области
проверить руками.

### Этап 9. Как у всех: чаты и длинные диалоги (текущий)

Уточнение цикла агента для небольших моделей: факты выполнения отделены от
того, что помещается в запрос. `ToolExecutionLedger` хранит состояние
вызовов одного ответа, `AgentTranscript` — полные шаги и их сокращённое
представление для протокола. Обрезка результата больше не разрешает
повторную запись и не превращает ошибку в успех. После операции с возможным
эффектом прежние чтения считаются устаревшими. Временную ошибку явно
читающего инструмента можно повторить один раз; ошибку записи — нельзя,
так как данные могли измениться до обрыва ответа. Отклонённый вызов с теми
же аргументами больше не спрашивает разрешения в этом ответе. Порядок полей
JSON не влияет на распознавание повтора. Отмена проверяется между вызовами
пакета и после разрешения пользователя. Контракты, ограничения и следующие
этапы — [docs/AGENT_EXECUTION.md](docs/AGENT_EXECUTION.md).

Цель владельца — нормальный инструмент со всеми основными функциями
AI-ассистентов в IDE.

**Сделано:**

- **Разные чаты** (`core.chat.ChatStore`): файл на диалог в
  `chats/<id>.json`, название — начало первого вопроса. «Новый чат»
  оставляет прежний в истории; меню вида ▾ → «История чатов» (последние
  30, открытый отмечен), «Удалить этот чат». При запуске открывается чат,
  открытый в прошлый раз. Пустой чат не хранится; храним до 100
  диалогов. Старый `chat.json` переносится в историю.
- **Окно модели по умолчанию — по имени модели** (`ModelConnection.guessWindow`):
  Claude — 200 тыс., GPT-4o/4.1/5, o-серия, Gemini — 128 тыс., DeepSeek —
  64 тыс., остальные — 32 768. Раньше 32 768 у всех, и с Claude + 99
  инструментами EDT-MCP модель теряла десятки старых сообщений.
- **Ответ сервера «не помещается»** — запрос повторяется сам, с бюджетом
  вдвое меньше (до трёх раз), а не ошибка.
- Строка в ленте при урезании — по-человечески: «Диалог длиннее окна
  модели — модель не видит самые старые сообщения (N)…».

- **Панель «История чатов»** (кнопка на панели вида): список чатов сбоку,
  щелчок открывает, контекстное меню — «Открыть», «Удалить».
- **Лимит шагов цикла агента — 50** (было 10): правка формы — десятки
  вызовов EDT-MCP. При остановке — «напишите «продолжай»».

- **Сжатие истории** (`ChatProvider.compactCount/summarize`, роль
  `ChatRole.SUMMARY`): когда история занимает больше половины бюджета
  запроса, перед ответом модель сжимает целые старые обмены в краткое
  содержание (цели, решения, затронутые модули, что осталось). Оно встаёт
  в ленту серым блоком «Краткое содержание диалога выше»; сообщения выше
  остаются видны, но модели дальше уходит краткое содержание. Не удалось
  сжать — ответ без сжатия (строка в ленте). Отбрасывание по окну
  осталось запасным путём.

- **Дифф и откат правок модели**: у ответа, где модель меняла модули, в
  заголовке «Изменения» — окно сравнения (`org.eclipse.compare`, текст
  сейчас / до ответа, только чтение) по каждому файлу — и «Откатить» —
  модули возвращаются к состоянию до ответа через буфер документа (Ctrl+Z
  в редакторе работает). Если файл меняли после правок модели —
  подтверждение. Спорно: точки отката живут до перезапуска EDT (в файл
  чата не пишутся); модель об откате не знает — после отката стоит
  написать ей об этом.

- **Что делает модель и токены** (`ChatSession.activity()`,
  `core.chat.TokenUsage`): в строке состояния, пока идёт ответ, — «думает…
  12 с», «пишет ответ… 3 с» или что делает инструмент («Читает модуль X…»),
  вкладка вида помечена занятой. После ответа — «контекст 45k из 200k ·
  ответ ↑120k ↓2,1k»: сколько окна занято после последнего шага и сколько
  токенов ушло и пришло за все шаги. Токены — из `usage` ответа (Anthropic
  — с кэшем подсказок; OpenAI-совместимые — если сервер шлёт `usage` в
  потоке; `stream_options` не передаём, чтобы старые шлюзы не отвергли
  запрос). Нет `usage` — оценка по длине текста со знаком «≈». В открытом
  чате до первого ответа — оценка занятого окна по истории.
- **`@` и `/` в поле ввода** (`core.chat.InputCompletion`,
  `core.chat.SlashCommand`, `ui.InputAssist` на JFace field assist): после
  `@` — модули проекта с поиском как в «Прикрепить модуль…», выбранный
  прикрепляется целиком; `/` в начале — команды `/new`, `/review [что
  смотреть]`, `/commit`, `/attach`, `/auto`. Неизвестная команда уходит
  модели как текст (путь «/home/…» — не команда).
- **Авторежим** (кнопка-переключатель с молнией рядом с полем ввода, `/auto`, кнопка «Авторежим» в
  вопросе о вызове): инструменты MCP вызываются без вопроса во всех чатах;
  в строке состояния — «авторежим». Хранится в настройках рабочей области
  (`autoApproveTools`). Правка модулей и git и так без вопроса.

- **Откат через git и честность модели**: `git_restore` — вернуть файлы
  или каталог объекта к HEAD (`git checkout HEAD -- путь` через JGit), с
  подтверждением; после отката EDT перечитывает файлы (`refreshLocal`).
  Новые файлы не удаляются. Раньше модель писала «откатил» и выдумывала
  команды `git checkout`, которых не выполняла: в правилах системного
  промпта — действовать только инструментами и не сообщать о
  несделанном.
- **«Project is building … retry» от EDT-MCP**: вызов MCP сам
  повторяется каждые 3 с до полутора минут, пока EDT собирает проект,
  вместо серии ошибок модели.

- **«Изменения» и «Откатить» для правок MCP**: пока идёт вызов
  инструмента MCP или меняющего встроенного (и 3 с после него, а после
  конца такого ответа — 10 с: EDT дописывает файлы с задержкой), вид
  слушает изменения ресурсов `src/` проекта (`IResourceChangeListener`,
  окно вызова — `core.tools.ToolActivity`). Такие файлы
  сравниваются с последним коммитом (`GitTools.headText`, переводы строк —
  как у файла), откат возвращает их к коммиту (с вопросом: пропадут и
  незакоммиченные правки пользователя в них), удалённые — создаёт заново,
  новые — удаляет. Проект не в git — показать нельзя, строка в состоянии.
  Правки пользователя или другого чата, пока модель пишет текст или
  вызывает читающие инструменты (ревью, вопросы), в список не попадают;
  попадут, только если совпали по времени с вызовом MCP.
- Открытый чат прокручивается в конец.
- **Ответ без инструментов — на виду.** Раньше, если сервер однажды
  отклонил запрос с инструментами, плагин молча отвечал без них до смены
  настроек — модель писала «смотрю», «делаю», ничего не вызывая. Теперь у
  каждого такого ответа строка «Инструменты — не передаются…», «Новый чат»
  пробует снова, в строке об отключении — ответ сервера. Для Anthropic
  ошибка про инструменты показывается как ошибка, без отключения: этот
  протокол инструменты поддерживает всегда.

- **Лента по порядку** (`core.chat.AnswerParts`, `ToolUse.at`): строка
  вызова стоит там, где модель его сделала, — между абзацами текста, а
  не стопкой под заголовком; место — сколько текста было до вызова, в
  начале следующей строки, хранится в `chat.json` (старые диалоги — как
  раньше, над текстом).
- **«Изменено: …»** под ответом: файлы, изменённые в ответе, — ссылки на
  сравнение каждого.
- Новый чат появляется в панели сразу с первым вопросом; колонка времени
  шире (на Windows обрезалась).
- **Токены по операциям**: `ToolUse.usage` — токены запроса к модели, на
  котором она решила вызвать инструмент (у первого вызова шага, чтобы не
  считать шаг дважды); в ленте « · ↑12k ↓310», оценка — с «≈»; хранится
  в `chat.json` (`tokens`), старые диалоги — без них.
- **Недавние модели — у каждого сервера свои** (`recentModels@хост`); если
  сервер отдал список моделей, недавних не из него в меню нет.
- **Ревью с маркерами**: инструмент `report_review` (`ReviewTools`) —
  находки списком: модуль, строка, серьёзность (error, warning, info),
  суть, как исправить. Модули проверяются, выдуманные не принимаются (модели
  — список отклонённых). Находки (`review/Finding`) — вложением `text/x-review`
  к ответу (хранятся в чате, модели не уходят): карточка в ленте; маркеры
  `io.github.hansglorias.edtai.ui.review` (problemmarker + textmarker) —
  значок у строки и «Проблемы»; новое ревью файла заменяет его маркеры,
  «убрать отметки» снимает все. Промпты ревью и правила инструментов
  просят передавать находки так.
  Перед публикацией проверяется форма всего `findings`: обязательный
  массив объектов, в каждом непустые строковые `module` и `title`,
  `line` — целое число от 1 до 2147483647, `severity` — строго
  `error`, `warning` или `info`. Необязательный `fix`, если передан,
  должен быть строкой. В обоих инструментах необязательный `project`
  тоже проверяется на строковый тип. `null` не заменяет отсутствие поля.
  Ошибка формы даже одной находки отклоняет весь вызов как ошибку
  аргументов; маркеры и вложение ревью не публикуются.
  При корректной форме неразрешимые ссылки (неизвестный модуль, путь
  вне проекта или не `.bsl`, нечитаемый файл, строка за пределами модуля)
  отклоняются по отдельности с причинами; остальные находки принимаются.
  Диапазон строки проверяется по несохранённому буферу, иначе по файлу,
  с подсчётом как в `read_module` (LF/CRLF/CR, завершающий перенос не
  добавляет пустую строку; пустой модуль содержит одну строку).
  Если отклонён весь непустой список — ошибка выполнения без публикации
  ревью и изменения прежних маркеров. Только явный `findings=[]` означает
  «замечаний нет»; как и раньше, он не снимает прежние маркеры файлов.
- **Ошибки вызовов**: `ToolUse.Problem` — вид ошибки, ставит `AgentLoop`
  (нет инструмента, аргументы, повтор, отказ) и `ToolException.problem()`
  (MCP: нет связи — `SERVER`, таймаут — `TIMEOUT`, иначе `FAILED`). В
  строке ленты — вид и первая строка причины (до 120 символов), полный
  текст — подсказкой (`MessageRenderer.Hint`). Хранится в `chat.json`
  (`problem`); старые диалоги — «ошибка: текст», как раньше.
- **Режим модели** (`AgentMode`): «Агент», «Авто» (MCP без вопроса),
  «План» (без инструментов правки, каждый вопрос с инструкцией плана),
  «Вопросы» (без инструментов правки). Одна кнопка-надпись (`Chip`) под
  полем ввода, цветом: «Авто» — оранжевый, «План» — бирюзовый, «Вопросы» —
  синий. Хранится в `agentMode`; у старых
  рабочих областей берётся из прежних флажков «Авторежим» и «Только
  вопросы». `/auto` и `/readonly` переключают «Авто» и «Вопросы». Счётчик
  «MCP 1/2» (`McpHub.counter`), ошибка подключения — красным.
- Формат следующего вопроса (`/answer`, `/options`, `/recommend`) убран:
  у агентов такого нет, «План» — режим модели. `/plan` включает «План»,
  с текстом — и сразу спрашивает. Чаты с прежними вложениями-режимами
  открываются как были.
- **Параллельные чаты**: у каждого живого диалога своя сессия, разрешения
  «в этом чате», правки модели и вопрос о разрешении. Вид показывает один;
  отвечающий уходит в фон и дописывается в свой файл, в панели у названия
  точка: жёлтая — отвечает, зелёная — ответил в фоне и ещё не открыт. «Новый чат» и открытие другого ответ не останавливают;
  закончивший фоновый чат сохраняется и отпускается. Очередь при
  переключении возвращается в поле ввода.

- **Интерфейс ленты**: больше трёх вызовов подряд сворачиваются в
  «→ Вызовы инструментов: N — показать» (пока ответ идёт — с последним
  вызовом под строкой); вопросы пользователя на лёгком цветном фоне;
  «Стоп» с красным значком. «Список…» моделей — диалог с поиском и
  прокруткой вместо меню, которое не помещалось на экран.

- **История чатов**: поиск над списком (`ChatStore.search` — все слова
  запроса в названии или тексте сообщений, без учёта регистра, «ё» = «е»;
  пауза 250 мс после набора); «Переименовать…» (F2) — название хранится
  отдельно в `chats/titles.json` (файл диалога переписывается на каждом
  сообщении), время изменения диалога не трогает; «Экспорт в Markdown…»
  (`core.chat.ChatMarkdown`) — вопросы с прикреплённым кодом, ответы с
  вызовами инструментов на своих местах. Для открытого чата — в меню вида.

- **«Только вопросы»**: флажок справа от строки состояния и `/readonly`
  (настройка рабочей области `readOnlyMode`, во всех чатах). У
  инструмента признак `Tool.modifies()`: `edit_module`, `git_restore` —
  да; инструмент MCP — по `annotations.readOnlyHint` из `tools/list`, без
  неё — по глаголу в начале имени (`get`, `list`, `read`, `search`, `find`,
  `go`…; незнакомый — правка). Такие инструменты модели не передаются, в
  системном промпте — `ProjectBrief.READ_ONLY_RULES`: правки показывать
  кодом в ответе, не выдавать за сделанные.

- **Команды**: `/explain`, `/tests` — готовый вопрос о коде: прикреплённый,
  иначе из активного редактора (`AttachedContext.fromEditor`), иначе —
  что названо после команды (модель ищет сама); ничего нет — подсказка в
  строке состояния. `/compact` — `ChatSession.compact()`: краткое
  содержание всего, что модель видит сейчас, встаёт в конец диалога
  (как автоматическое сжатие, но по команде; «Стоп» — без изменений,
  ошибка — в ленте). `/mcp` — `McpHub.status` (`ServerStatus`: состояние,
  ошибка, имя сервера, все инструменты, `allowed()` по фильтру) в окне
  `McpStatusDialog`: дерево «сервер → инструменты» с колонками «Доступ»
  (читает / меняет проект по `McpToolInfo.modifies` / не передаётся),
  «Состояние, описание», цветной значок состояния, полное описание
  выбранного внизу, кнопка «Настройки MCP…». Текстом — `McpHub.describe`.
- **Название чата моделью**: после первого ответа без названия —
  `ChatProvider.title` (вопрос и начало ответа, 64 токена,
  `ModelChatProvider.cleanTitle` убирает кавычки, Markdown, «Название:»),
  по разу на чат; результат — в `titles.json`, как ручное
  переименование, ручное не перезаписывается. Настройка
  `generateChatTitles` (по умолчанию да).

- **Вложения** (`core.chat.Attachment`, `ChatMessage.attachments`):
  кнопка у поля ввода (`FileDialog`, несколько файлов), Ctrl+V /
  Shift+Insert — `ImageTransfer` (скриншот → PNG через `ImageLoader`) или
  `FileTransfer`, перетаскивание файлов на поле (`DropTarget`). Картинка
  по расширению (PNG, JPEG, GIF, WebP, до 3,75 МБ — после base64 5 МБ,
  предел Anthropic) — блоком изображения перед текстом вопроса
  (Anthropic `image`/`base64`, OpenAI `image_url` с data-URL); иначе
  текст (UTF-8, иначе Windows-1251; с `\0` — не текст) — в тексте вопроса
  блоком кода. Документы (`core.documents.DocumentText`, без библиотек) —
  их текстом, тип `text/x-document`, в вопросе «Файл X (текст
  документа)»: .docx — абзацы, заголовки `#`, пункты `-`, таблицы
  Markdown; .xlsx — листы строками через табуляцию (общие строки, даты по
  формату ячейки → ISO); .pptx — по слайдам; .odt/.ods/.odp — то же из
  `content.xml` (повторы пустых ячеек и строк обрезаются); PDF
  (`PdfText`) — объекты и потоки объектов, Flate, дерево страниц и формы,
  `ToUnicode`, а без него — WinAnsi и `/Differences`; строки и колонки —
  по матрице текста и ширинам глифов (колонки таблицы — табуляцией).
  Зашифрованный PDF и скан — понятная ошибка; .doc/.xls/.ppt — подсказка
  пересохранить. Пакет распаковывается до 100 МБ, файл — до 30 МБ, текст
  больше 200 тыс. символов обрезается с пометкой. В запросе картинка считается за 1600 токенов, а не по
  длине base64; у старых сообщений при нехватке окна вложения
  отбрасываются вместе с кодом. Хранятся в `chat.json` (картинки — base64).

- **Ctrl+V с картинкой в EDT**: нажатие перехватывает команда верстака
  «Вставить» и до поля ввода не доходит — у вида свой обработчик
  (`setGlobalActionHandler(PASTE)`): в поле ввода картинка или файлы из
  буфера прикладываются, иначе — обычная вставка текста. У поля своё
  меню: «Вставить» с тем же поведением, «Приложить файлы…».
- **Оформление**: свои значки (`icons/`, 16 px и `@2x`, класс `Icons`) —
  скрепка у вложений, боковая панель у «Истории чатов», молния у авторежима,
  лист с карандашом у «Нового чата», стрелка у «Отправить» (значок у кнопки
  есть всегда: на Windows кнопка без картинки после «Стоп» сдвигала
  текст). «Новый чат» — и в заголовке панели «Чаты», и в её меню. В ленте
  поля шире, межстрочный интервал +2 px, имя автора — жирным на пункт
  крупнее.

- **Миниатюры картинок** в ленте у вопроса (до 240×140, пропорции
  сохраняются, маленькие не растягиваются): место — символ U+FFFC с
  `GlyphMetrics`, рисует `PaintObjectListener` (`event.y` — верх места под
  картинку, не строки). Щелчок — картинка целиком во временном файле
  программой системы (`Program.launch`).
- **Узкая полоса прокрутки** (`ThinScrollBar`): у ленты нет системной
  (на Windows 17 px и не меняется), поверх правого поля — своя, 8 px,
  ползунок цвета смеси фона и текста (виден в светлой и тёмной теме),
  тянется мышью, щелчок мимо — прыжок; колесо обрабатывается само:
  StyledText без системной полосы им не прокручивается.
- **Единый стиль значков**: контуры на сетке 16×16, линия 1,35 px,
  скруглённые концы, без теней и градиентов; PNG 16 px и `@2x` 32 px.
  Действия — серо-синие, бренд — бирюзовый; состояния сохраняют смысловой
  цвет. Исходная геометрия и генератор без зависимостей —
  `tools/GenerateIcons.java`, палитра — в `icons/README.md`.
  Верхняя панель: новый чат (лист с карандашом), список чатов (боковая
  панель), настройки (ползунки). Прикрепление модуля — через «+» у ввода,
  `@` и `/attach`, без дублирующей кнопки в заголовке. Документы в ленте
  и поиске модулей используют свой общий значок файла вместо значков ОС.
  Маркеры ревью сохраняют прежний тип и severity, но имеют собственные
  annotationTypes для трёх уровней: диалог с крестом, «!» или «i».
  В окне «Проблемы» — общий бирюзовый диалог с галочкой. Отметки на
  линейках включены по умолчанию, подчёркивание кода выключено;
  оформление можно изменить в стандартных настройках аннотаций Eclipse.

- **Скиллы** (`core.skills`): файл Markdown с заголовком `---`
  (`name`, `description`) и инструкцией. Источники по возрастанию
  приоритета: встроенные (`skills/builtin/*.md` в ядре, список —
  `SkillLibrary.BUILT_IN`), свои (`<state>/skills`), проекта
  (`<проект>/.edtai/skills`); одинаковое имя — побеждает поздний. Имя —
  латиница, цифры, дефис; имена встроенных команд заняты. Модель видит
  список «имя — описание» в системном промпте (если инструменты включены)
  и читает инструкцию инструментом `skill`; `save_skill` пишет свой скилл
  (проект не меняют — доступны и в режиме «только вопросы»). Команда
  `/имя [текст]` — вопрос с инструкцией вложением (`Attachment.skill`, в
  ленте «скилл имя»); `/skill <описание>` — с вложенным `create-skill`;
  `/skills` — окно `SkillsDialog`: таблица всех скиллов с галочками
  (выключенные — `disabledSkills` в настройках, имена через перевод
  строки; `SkillLibrary.all()` их пропускает: нет в промпте, `/имя` и
  `skill` их не находят, `everything()` — для окна), текст выбранного
  внизу, «Открыть папку своих…». Подсказки после `/` — команды и
  включённые скиллы.
- **Встроенный набор из практики** (по набору правил для агента,
  накопленному на проектах 1С с Claude Code): `bsl-style`, `query-style`,
  `edt-project`, `access-rights`, `release-update`, `html-field`,
  `commit-message`, `live-base`, `platform-gotchas`. Переписаны под
  плагин: инструменты `read_module`/`edit_module`/`git_*` и EDT-MCP вместо
  shell, без ссылок на файлы рядом (`../../knowledge`) — ссылки на другие
  скиллы по имени; корпоративный профиль и шаблоны карточки проекта не
  взяты. `query-optimize` и `code-standards` согласованы с ними (индекс ВТ
  — только для большой таблицы, блокировка — не «на всякий случай»).
  Общие правила работы (границы задачи, что только после «да», не гадать,
  найденное попутно — три группы) — в `ProjectBrief.TOOL_RULES`, в
  системном промпте при включённых инструментах. «Сообщение коммита»
  пишется по скиллу `commit-message`.

- **Файлы в ответе** (`core.tools.FileTools`, инструмент `attach_file`:
  имя и содержимое): `.docx` — `core.documents.DocxWriter` из Markdown
  (свой zip из XML без библиотек: стили Heading1–4, Quote, Code,
  ListParagraph, нумерация — у каждого нумерованного списка своя с
  единицы, таблицы с шапкой и выравниванием, ссылки, A4 с полями 2 см);
  `.xlsx` — `XlsxWriter`: таблицы Markdown — листы (имя из заголовка над
  таблицей, без `[]:*?/\`, до 31 знака, без повторов), без таблиц — CSV
  (разделитель по первой строке, кавычки); число («1 234,5», без нуля
  впереди и до 15 цифр) — число, `ДД.ММ.ГГГГ` — дата (формат 14),
  «=» с функцией по-английски или ссылкой на ячейку — формула; шапка —
  жирная с заливкой, закреплена, автофильтр (`_xlnm._FilterDatabase`),
  ширина колонок по тексту, строки — inline strings; `.pptx` —
  `PptxWriter`: заголовок 1–2 уровня или `---` — новый слайд, первый
  слайд с заголовком и одной строкой — титульный; надписи без
  заполнителей (один пустой макет, своя тема), пункты с маркерами и
  `buAutoNum`, код Consolas, таблица — `a:tbl` с шапкой; шрифт 24…14 пт
  по объёму. Разбор блоков Markdown для всех трёх — `MarkdownBlocks`,
  zip и экранирование — `Ooxml`. Текстовые форматы — как есть (CSV — с
  BOM); PDF (нужно встраивать шрифт с кириллицей), .doc, .xls,
  картинки, архивы — отказ с подсказкой. Имя — без каталогов и запрещённых в
  Windows символов, до 120 знаков. Файл едет в `Tool.Result.file` →
  `ToolUse.file` → `ChatSession` переносит его в `attachments` ответа (в
  вызове не хранится). У ответа вложения модели не уходят (`images()`
  пуст, `modelText` без них), при нехватке окна не считаются. В ленте —
  строка-карточка с фоном кода: свой контурный значок документа, имя (открыть), размер,
  «Сохранить…» (`FileDialog`, последний каталог запоминается),
  «Открыть» (временный файл, `Program.launch`). В экспорте Markdown —
  «Файл: `имя`». Проект не меняет — есть и в режиме «только вопросы».

- **Очередь сообщений** (`QueueBar` над панелью контекста): пока идёт
  ответ, Enter или кнопка у поля (при набранном тексте — стрелка с
  подсказкой «В очередь», при пустом поле — «Стоп») кладут сообщение в
  очередь вместе с прикреплённым: фрагменты переходят с панели контекста
  в очередь, не освобождаясь, и снимаются по лимиту при отправке. Команды
  без вопроса модели (`/model`, `/auto`…) выполняются сразу, `/explain` и
  `/tests` берут выделение в момент постановки. Ответ закончился (`DONE`)
  — уходит первое из очереди, следующее — после его ответа. Ответ
  остановлен или оборвался — вся очередь возвращается в поле ввода (к
  набранному, через пустую строку) и на панель контекста: решает
  пользователь. Пункты меню вида («Ревью…», «Сообщение коммита») во время
  ответа тоже в очередь.
- **Выбор модели в поле ввода** (`core.settings.ModelChoices`): кнопка
  `SWT.DROP_DOWN` с коротким именем (без префикса поставщика, до 28
  знаков) справа от кнопок режимов, рядом с «Отправить». Меню — текущая,
  недавние (до 8, `recentModels` в настройках; при смене в недавние
  попадает и прежняя), затем модели сервера по алфавиту; строка о
  загрузке или ошибке списка, «Обновить список», «Настройки модели…».
  Список (`ModelClient.models`) грузится в фоне один раз на сервер, когда
  указатель над кнопкой, при открытии меню или по `/model`; смена адреса
  его сбрасывает. Выбор сохраняет поле «Модель» настроек
  (`AiSettings.withModel`) — для всех чатов, со следующего запроса; окно
  модели, заданное явно, остаётся. `/model имя` — точное имя, иначе
  единственная, где есть набранное; несколько — подсказка; ни одной —
  имя как набрано (сервер может не отдавать список). Профили с разными
  серверами и токенами — не сделаны.
- **Индикатор MCP** вместо строк об ошибке в каждом ответе: кнопка «MCP»
  в строке состояния с точкой — `McpHub.health(lastStatus(серверы))`:
  `McpHub` запоминает итог последнего подключения каждого сервера (при
  ответе и `/mcp`), сервер с изменёнными настройками — «ещё не
  проверялся», `reset()` всё забывает. Хоть один не подключился —
  красная, все включённые подключены — зелёная, иначе серая; подсказка —
  строка на сервер. При открытии вида и после изменения настроек
  включённые серверы проверяются в фоне. Щелчок — окно `/mcp`.
- **Компоновка вида**: список чатов — боковая панель на всю высоту
  (`SashForm`: панель | колонка чата); справа лента без рамки, панели

  одна скруглённая рамка (рисуется сама, цвет поля, в фокусе — цвет

  ответ, приглушённая стрелка — нечего отправлять; подпись — в подсказке.

- **Бренд EDT AI**: вид называется «EDT AI» (категория видов — тоже),
