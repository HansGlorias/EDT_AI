# AGENTS.md

Инструкция для ИИ-агентов (Codex и других), которые продолжают разработку
EDT AI. Правила проекта — в [CLAUDE.md](CLAUDE.md) (читай его целиком, он
обязателен и для тебя), что и зачем делаем — в [SPEC.md](SPEC.md), план —
в [docs/ROADMAP.md](docs/ROADMAP.md).

## Что это

Плагин для 1C:EDT (Eclipse 4.30, Java 17): чат с языковой моделью в виде
EDT. Модель читает и правит модули проекта инструментами, вызывает
MCP-серверы (EDT-MCP), делает ревью с маркерами, ведёт несколько чатов
параллельно. Работает с OpenAI-совместимыми серверами (DeepSeek, Qwen,
Ollama, LM Studio, vLLM) и Anthropic. Пользователь — разработчик 1С;
интерфейс, сообщения коммитов и PR — по-русски.

## Сборка и проверка

Локально запускай новые/изменённые тесты и затронутые соседние сценарии.
При правках UI проверяй затронутые UI-сценарии; при чистых правках core
не запускай UI-набор. Для изменений только документации достаточно
проверки diff и ссылок, без запуска Eclipse.

Полный `verify` (core + UI) на Windows и Ubuntu обязателен в CI перед
мержем. Полный локальный прогон нужен только для диагностики конкретного
сбоя, при изменении сборки или по запросу владельца; перед каждым пушем
он не требуется. Точные команды — в [docs/TESTING.md](docs/TESTING.md).

Не повторяй зелёные проверки того же SHA без новых изменений или
конкретной причины. Логи сохраняй в файл, читай итог и сведения о сбоях.

- Только `./mvnw` (Maven 3.9.11), не системный `mvn`.
- Первая сборка качает target platform Eclipse 2023-12 (~1 ГБ) с
  `download.eclipse.org` и плагины с Maven Central. Потом можно `-o`.
- `LANG=C.UTF-8` обязателен: в тестах пути с кириллицей.
- UI-тесты (SWT) — только под `xvfb-run` на Linux без дисплея.
- Одним тестом: `-Dtest=ИмяТеста`
  и `-pl releng/edtai.target,<модуль>,<тесты> -am` (без target platform
  Tycho не собирает).
- Отчёты: `tests/*/target/surefire-reports/`; скриншоты UI-тестов —
  `tests/io.github.hansglorias.edtai.ui.tests/target/screenshots/`
  (смотри только затронутые состояния). Отчёты и снимки доступны также
  в артефактах CI.
- Update-site zip для пользователя бери из успешного CI нужного SHA
  ветки `main` (артефакт `edtai-update-site`), без повторной локальной
  сборки ради архива. Как сверить SHA — в [docs/TESTING.md](docs/TESTING.md).
- Облачное окружение: подготовь его скриптом `tools/agent-setup.sh` (JDK,
  xvfb, скачивание зависимостей заранее).

## Как работаем

1. Одна задача — одна ветка и один небольшой PR в `main`.
2. Код + тесты (логика — в `core`, тест в `tests/…core.tests`; UI — тест в
   `tests/…ui.tests`) + README/SPEC, если меняется поведение.
3. Целевые локальные проверки (для документации — diff/ссылки) → коммит
   → пуш → PR.
4. CI (`.github/workflows/build.yml`) собирает на `ubuntu-latest` и
   `windows-latest`: полный wrapper `verify`, core + UI; мерж — только
   когда оба зелёные для актуальной версии PR. Упал — разберись в причине
   по логу, не перезапускай вслепую и не отключай тесты или платформы.
5. После мержа — update-site зип пользователю, он проверяет в EDT руками
   по чек-листу из PR.

Коммиты: по-русски, с маленькой буквы, без точки в конце, суть изменения
(«точка состояния у чатов и недавние модели по серверам»).
Личный навык `commit-message-style` здесь не применять: он относится к
рабочему проекту владельца. В EDT AI приоритет — точное описание изменения,
понятное следующему ИИ-агенту; при необходимости добавить причину и границы
изменения в тело коммита, без имитации разговорного стиля владельца.

PR — три раздела: «Что сделано», «Что проверено автотестами», «Проверить
руками (Windows, Astra)» — чек-листом.

## Грабли, на которые уже наступали

- Windows: многострочный `Text`/`StyledText` отдаёт `\r\n`. В коде — 
  `Text.DELIMITER`, в тестах — нормализуй `\r\n` → `\n`. Два раза CI на
  Windows падал именно на этом.
- Тест не должен зависеть от состояния, оставшегося от другого теста
  (панель чатов открыта/закрыта, настройки): выставляй сам.
- Не используй API новее Eclipse 4.30 и SWT `Browser`; `core` не зависит
  от SWT/JFace/`org.eclipse.ui`; сторонние библиотеки — нельзя.
- Токен — только в Secure Storage, никогда в логах, настройках,
  `toString()`. Репозиторий публичный: в тестах только `localhost`,
  `example.invalid`.
- Новые пакеты `core` — добавь в `Export-Package` в `META-INF/MANIFEST.MF`,
  иначе UI не скомпилируется.
- `ChatView` большой (~3000 строк). Правь точечно, читай код вокруг правки.
  Состояние диалога — в `ChatView.Live` (сессия, разрешения, правки
  модели), открытый — `current`; отвечающие в фоне живут в `lives`.

## Карта кода

`bundles/io.github.hansglorias.edtai.core` — логика без UI:
- `chat` — сообщения, сессия (`ChatSession`), история чатов (`ChatStore`,
  `ChatHistoryFile`), режим модели (`AgentMode`: Агент, Авто, План,
  Вопросы), вызовы инструментов в ленте (`ToolUse`: токены шага, вид
  ошибки), команды поля ввода (`SlashCommand`).
- `llm` — клиент модели (`ModelClient`, адаптеры OpenAI/Anthropic, SSE),
  цикл агента с инструментами (`AgentLoop`), бюджет окна (`RequestBudget`).
- `tools` — встроенные инструменты: чтение проекта (`ProjectTools`),
  правка модулей (`EditTools`), git, файлы, скиллы, итог ревью
  (`ReviewTools`), правила для модели (`ProjectBrief.TOOL_RULES`).
- `mcp` — клиент MCP (stdio/HTTP), `McpHub`.
- `skills` — скиллы (встроенные в `skills/builtin/*.md`, свои, проекта).
- `review` — находки ревью (`Finding`).
- `context`, `documents`, `markdown`, `settings`, `tls`, `json`.

`bundles/io.github.hansglorias.edtai.ui` — Eclipse UI:
- `ChatView` — вид чата; `MessageRenderer` — лента (StyledText);
  `ChatHistoryPanel` — список чатов с точками состояния; `Chip` —
  кнопки-надписи под полем ввода; `ReviewMarkers` — маркеры ревью;
  `AiPreferencePage` — настройки; обработчики команд редактора и окна
  коммита.

## Следующая задача: работа на лёгких моделях

Цель — чтобы на маленькой модели (Qwen 7–14B, окно 8–32k) плагин не
тратил окно на служебное и модель меньше ошибалась в 1С.

Замер служебной части запроса (без MCP): описания 13 встроенных
инструментов ~8 300 символов, список скиллов ~2 900, `TOOL_RULES` ~2 250,
системный промпт и сведения о проекте ~1 000 — всего ~14 500 символов,
~5 000 токенов на каждый шаг. MCP (EDT-MCP — десятки инструментов) —
сверху, вероятно больше всего.

План (согласован с пользователем как направление, начинать с 1, 2, 4, 6):
1. Режим «лёгкая модель» (авто при окне ≤ 32k или флажком в настройках):
   короткие описания инструментов, набор из 6 основных (read_module,
   search_code, list_objects, edit_module, skill, report_review).
2. Скиллы по запросу: в промпте — только имена, текст — инструментом
   `skill`.
3. MCP: по умолчанию только выбранные инструменты, показать, сколько
   токенов занимает каждый сервер.
4. Короткие правила вместо `TOOL_RULES` (5 строк).
5. Шпаргалка синтаксиса BSL и запрет выдумывать методы платформы; проверка
   блоков ```bsl в ответе (английские ключевые слова, непарные
   `Процедура…КонецПроцедуры`) — попросить модель исправить.
6. Счётчик служебных токенов («служебное: 4,8k из 32k») в подсказке модели
   или строке состояния; тест, что в лёгком режиме служебное ≤ ~5 000
   символов.

Дальше в плане: проверка Qwen в сети пользователя (без кода — по чек-листу
в ROADMAP), оркестрация моделей — отложена.
