# Права и доступ

Права — зона владельца системы и службы ИБ. Ошибка здесь не баг, а инцидент.

## 1. Код не наделяет пользователей полномочиями

Код не пишет состав групп доступа (ни при записи объектов, ни в
обработчиках обновления, ни «переносом» из группы в группу) и не выдаёт роли
пользователям ИБ. Состав групп назначают регламентным путём (заявка,
согласование) или администратор руками.

Можно: создавать поставляемые профили и наполнять их ролями, создавать
пустые группы доступа под объекты.

Почему: выдача групп кодом из обработчика обновления однажды дала
администрирование трём десяткам разработчиков. Нашёл такой код — вырезать,
не комментировать.

## 2. Правки ролей и профилей — только после «да»

- Похоже на нехватку прав: сначала посмотри, какой профиль и какие группы
  доступа у пользователя. Пустой экран из-за не того профиля чинится не
  правкой роли.
- Правку роли предлагай словами (какой объект, какое право, почему), делай
  после согласия.

## 3. Привилегированный режим — последнее средство

Порядок выбора:
1. Роль в профиль пользователя, если ему не хватает прав на действие.
2. Технический пользователь с технической ролью без РЛС — для регламентных
   заданий и интеграций.
3. Привилегированный режим — только где без него не работает платформа или
   БСП (безопасное хранилище). Окно включения узкое, вокруг одной операции.
   Кажется, что без него никак, — сначала спроси.

Обходить привилегированным режимом РЛС («задание работает не от того
пользователя») нельзя.

## 4. РЛС в БСП считается по группе доступа

РЛС на роли ничего не гарантирует. БСП проверяет `#ПоЗначениям` отдельно по
каждой группе доступа, которая даёт право на таблицу. Если в профиле группы
нет нужного вида доступа, по этому виду в группе разрешено всё, а группы
пользователя объединяются по ИЛИ.

«Кто что видит» проверяй по трём пунктам: роль и её РЛС; виды доступа в
профиле (`ОписаниеПрофиля.ВидыДоступа`); значения доступа в группе. Вывод
«дыра закрыта» — только после всех трёх.

Ограничение объекта в БСП задаётся одним из двух способов, не обоими: объект
регистрируется в `ПриЗаполненииСписковСОграничениемДоступа` (тогда нужен
`ПриЗаполненииОграниченияДоступа` в модуле менеджера, иначе «Метод объекта не
обнаружен»), или ограничение целиком описано в роли шаблоном `#ПоЗначениям`.

## 5. Rights.rights и флаг «для новых объектов»

- При `setForNewObjects=true` в файле лежат только снятые права, а объекты,
  которых в файле нет, получают ВСЕ права, включая интерактивное удаление.
  Флаг уместен только на административной роли.
- Интерактивного удаления не должно быть ни у одной бизнес-роли. На
  административной роли с флагом снимай его руками у каждого нового объекта
  (справочники: `InteractiveDelete`, `…Marked`, `…PredefinedData`,
  `…MarkedPredefinedData`; документы, процессы, задачи — 2 права).
- Права на веб- и HTTP-сервисы задаются на операциях и методах
  (`WebService.X.Operation.Y`, `HTTPService.X.URLTemplate.T.Method.M`).
- Режим технического специалиста — только у администратора данных, ни в
  одном поставляемом профиле. Роли внешних отчётов и обработок по умолчанию
  никому.

## 6. Технический пользователь

- Под регламентное задание или интеграцию: отдельная техническая роль и
  профиль, группа доступа с этим профилем.
- **Не помечай его «Служебный»**, если роли должна раздать БСП: служебным БСП
  роли из профилей не разворачивает.
- Не входит интерактивно: без аутентификации,
  `ПоказыватьВСпискеВыбора = Ложь`.
- Любая запись идёт через подписки БСП, которым нужны права чтения служебных
  регистров и констант. Не хватает — смотри стек ошибки, а не давай
  административные права.
- Старые технические роли, сделанные до вас, попутно не правь: перечисли
  расхождения.

## 7. Расширения

- Флажок «для новых объектов» у ролей основной конфигурации на собственные
  объекты расширения не действует.
- Права администратора на объекты расширения закладывай в само расширение
  (заимствовать роль и дописать права), а не выдавай руками в базе.
